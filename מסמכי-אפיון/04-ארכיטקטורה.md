# ארכיטקטורה

**חלק מ:** אפיון פרויקט R&D — מערכת גנרית לניהול, חקירה ואבחון לוגים
**שלב:** תוצר מס' 4 מתוך 12 בסעיף 23 של האפיון המקורי
**תאריך:** 2026-08-17
**מבוסס על:** [02-אפיון-המוצר.md](02-אפיון-המוצר.md), [03-הגדרת-V1.md](03-הגדרת-V1.md), ושיחת סקופינג ארכיטקטוני עם בעלת הפרויקט (2026-08-17)

## 1. סקירה כללית

V1 ייבנה כ-**Modular Monolith** ב-.NET: תהליך הרצה יחיד שמכיל Web API, Blazor Server UI, ומנוע ניתוח פנימי (Analysis Engine כ-`BackgroundService`), מול מסד נתונים יחסי אחד (SQL Server). המבנה מחולק לרכיבים לוגיים ברורים (Domain / Infrastructure / Analysis / Web / Client) שכל אחד ניתן להבנה ולבדיקה בנפרד, אבל נפרסים ורצים כתהליך אחד — כדי להתאים לפיתוח עצמאי, ריצה מקומית, ונפח נתונים של סימולציה.

## 2. חלופות שנשקלו

| חלופה | תיאור | למה לא נבחרה (ל-V1) |
|---|---|---|
| **A — Modular Monolith** ✅ נבחרה | תהליך .NET אחד: API+UI+Analysis Engine פנימי, SQL Server אחד | — |
| B — שירותים מופרדים | Ingestion API / Query API / UI / Analysis Worker כתהליכים נפרדים | תקורת deploy/תחזוקה לא מוצדקת לפיתוח עצמאי שרץ מקומית; פיצול בעתיד אפשרי בלי לשנות סכימה |
| C — מבוסס תור-הודעות | Ingestion כותב לתור (RabbitMQ/Azure Service Bus), consumer נפרד כותב ל-DB ומפעיל ניתוח | מוסיף רכיב תשתית שלם שלא מוצדק בנפח V1 (2 אפליקציות סימולציה); relevant יותר כש-scale אמיתי ייכנס לתמונה ב-V2+ |

**עקרון מנחה:** הבחירה ב-A לא נועלת את הדלת לפיצול עתידי — Analysis Engine בנוי כרכיב לוגי נפרד (`LogsPlatform.Analysis`, ראו סעיף 3) שניתן להוציא לתהליך/worker נפרד ב-V2 בלי לשנות את מודל הנתונים או את חוזה ה-API.

## 3. רכיבי המערכת

לכל רכיב: מה הוא עושה, איך משתמשים בו, ובמה הוא תלוי — כדי שאפשר יהיה לשנות פנימיות בלי לשבור צרכנים.

### `LogsPlatform.Domain`
**מה:** ישויות הליבה (Application, Module, ScreenService, Process, Operation, Environment, Version, Deployment, Customer/Tenant, Event, ExceptionGroup, Baseline, Finding, Evidence) + חוזי interface (למשל `IAnomalyDetector`). **תלוי ב:** כלום — זהו הליבה הטהורה, ללא תלות ב-EF Core/ASP.NET.

### `LogsPlatform.Infrastructure`
**מה:** מימוש גישה לנתונים — EF Core `DbContext`, migrations, repositories למימוש הישויות מ-Domain. **משתמשים בו דרך:** repository interfaces שמוגדרים ב-Domain (Dependency Inversion — Infrastructure תלוי ב-Domain, לא להפך). **תלוי ב:** Domain, SQL Server.

### `LogsPlatform.Analysis`
**מה:** מנוע הניתוח — חישוב Baseline, 4 גלאי הקורלציה/אנומליה שנבחרו ל-V1 (Deployment→Error Spike, Missing Activity, Customer Anomaly, Exception→Downstream Failure), ובניית Findings עם תיוג Fact/Observation/Hypothesis מפורש. **משתמשים בו דרך:** ממשק `IAnalysisRunner` שה-`BackgroundService` ב-Web קורא לו בטיימר. **תלוי ב:** Domain (לקריאה/כתיבה של Events/Baselines/Findings דרך repositories), לא תלוי ב-Web/UI כלל — ניתן להריץ ולבדוק את המנוע לגמרי בנפרד מה-HTTP layer.

### `LogsPlatform.Web`
**מה:** מארח את הכל — controllers ל-Ingestion API + Query API + Application-Structure Admin API, דפי Blazor Server (UI), ורישום ה-`BackgroundService` שמפעיל את `LogsPlatform.Analysis` בתזמון קבוע. **תלוי ב:** Domain, Infrastructure, Analysis.

### `LogsPlatform.Client`
**מה:** ספריית client קלה ל-.NET שעוטפת קריאות HTTP ל-Ingestion API, + adapter ל-Serilog (`ILogEventSink`). פרויקט נפרד כדי שאפשר יהיה למקד/להפיץ אותו בנפרד בעתיד (למשל כ-NuGet). **תלוי ב:** כלום מהפתרון עצמו — רק בחוזה ה-API (JSON contract משותף).

### פרויקט בדיקות: `SyntheticDataGenerator`
**מה:** אפליקציית קונסולה/שירות שמדמה 2 Applications ומזינה את 6 תרחישי האנומליה (סעיף 4 ב-[03-הגדרת-V1.md](03-הגדרת-V1.md)) — פועלת כלקוח לגיטימי מול ה-Ingestion API (לא כותבת ל-DB ישירות), כדי שהבדיקה תכסה את כל השרשרת מקצה-לקצה. **תלוי ב:** `LogsPlatform.Client`.

## 4. זרימת נתונים

```
אפליקציית לקוח (Synthetic Data Generator ב-V1)
   → LogsPlatform.Client (HTTP/Serilog sink)
   → Ingestion API (LogsPlatform.Web)
   → ולידציה + כתיבה ל-DB (Events + הפניות להיררכיה שכבר הוגדרה)

Analysis BackgroundService (טיימר, כל כמה דקות)
   → LogsPlatform.Analysis: קורא Events חדשים מאז ריצה קודמת
   → מעדכן Baseline (ממוצע/סטיית-תקן, bucketing שעה-ביום, per Operation/ExceptionGroup)
   → מריץ 4 גלאי הקורלציה/אנומליה
   → כותב/מעדכן Findings + Evidence (עם Fact/Observation/Hypothesis מסומן)

Blazor UI (LogsPlatform.Web)
   → Query API (אותו תהליך, אותו DB)
   → חיפוש/סינון, Timeline, Exceptions, מסך Findings/What's Unusual, Drill-Down
```

הערה מרכזית: ה-Analysis Engine **לא** רץ סינכרונית על כל אירוע נכנס (זה היה יקר ומייצר עומס על ה-ingestion path) — הוא רץ במחזוריות קבועה על כל מה שהצטבר. זה תואם לעיקרון ה-Baseline מהאפיון (התנהגות נלמדת מצטברת, לא תגובה מיידית לכל אירוע בודד).

## 5. Storage — גישה כללית

**בחירה:** SQL Server יחסי, עם עמודות ממודדות (indexed) לשדות הסינון הנפוצים (Timestamp, Severity, ApplicationId, EnvironmentId, ModuleId, ScreenServiceId, ProcessId, OperationId, CorrelationId, TraceId, UserId, CustomerId, Duration) + עמודת JSON (`nvarchar(max)` עם `OPENJSON`/computed columns לפי הצורך) ל-Metadata חופשי.

**למה לא מנוע לוגים ייעודי (כמו Elasticsearch/Loki-style):** בנפח V1 (2 אפליקציות סימולציה, נתוני R&D) אין הצדקה לתפעל רכיב תשתית נוסף. SQL Server עם אינדוקס נכון + full-text search מובנה מספיק לצרכי החיפוש/הסינון של V1. אם/כש-scale אמיתי ייכנס לתמונה (V2+, עם אפליקציה אמיתית), זו תהיה נקודת הערכה מחדש מפורשת — לא הנחת-יסוד של V1.

**מודל הנתונים המלא** (טבלאות, שדות, מפתחות, יחסים) הוא התוצר הבא בסדרה (Data Model, תוצר 5 מתוך 12) — כאן רק הגישה הכללית.

## 6. Ingestion & API — גישה כללית

HTTP API קנייני (JSON), עם endpoint ל-ingestion בודד/batch, מאומת ב-API key (per-Application). ה-.NET client (`LogsPlatform.Client`) עוטף את זה + מספק Serilog sink adapter, כדי שחיבור אפליקציית .NET יהיה תרגיל של כמה שורות קונפיגורציה. **OTLP נדחה ל-V2** (כפי שנקבע ב-[03-הגדרת-V1.md](03-הגדרת-V1.md)) — אך שמות השדות (Severity, Service-hierarchy) נבנים כבר עכשיו תואמים-מראש למוסכמות OpenTelemetry, כדי שאימוץ OTLP עתידי (דרך Collector+adapter, כפי שהמחקר המליץ) לא ידרוש שינוי סכימה. **חוזה ה-API המלא** הוא תוצר נפרד (Ingestion/API Design, תוצר 6).

## 7. Analysis Engine / Background Processing

`BackgroundService` יחיד בתוך `LogsPlatform.Web` שמפעיל בטיימר קבוע (למשל כל 5 דקות, קונפיגורבילי) את `IAnalysisRunner` מ-`LogsPlatform.Analysis`. הריצה כוללת שני שלבים לוגיים נפרדים: (1) עדכון Baseline מצטבר, (2) הרצת גלאי האנומליה/קורלציה מול ה-Baseline המעודכן. הפרדה זו מאפשרת בעתיד להריץ אותם בתדירויות שונות (Baseline update פחות תדיר, זיהוי אנומליות תדיר יותר) בלי לשנות מבנה. **תכנון הגלאים עצמם, פורמט ה-Finding, ומודל ה-Evidence** הוא תוצר נפרד (Analysis/Anomaly Detection Design, תוצר 7).

## 8. Application Model

ההיררכיה (Application→Module→Screen/Service→Process→Operation) + Environments/Versions/Deployments/Customers הן ישויות ראשונות-מעמד ב-`Domain`, מנוהלות דרך Admin API + מסכי Blazor — **לא קונפיגורציה בקוד**. זהו הרכיב שהמחקר זיהה כהבדלה התחרותית המרכזית (ראו [02-אפיון-המוצר.md](02-אפיון-המוצר.md) סעיף 2) ולכן מקבל טבלאות יחסיות מלאות ולא ייצוג כ-properties/tags חופשיים.

## 9. Authentication / Authorization

- **Ingestion API:** API key per-Application (נשלח ב-header), נבדק מול טבלת Applications.
- **UI/Admin:** אימות משתמש/סיסמה בסיסי (ASP.NET Core Identity או מימוש מינימלי dependency-free) — **בלי** RBAC גרנולרי ב-V1, כפי שנקבע.
- **בידוד Environment:** נאכף ב-**query layer** (כל repository/query מסונן חובה לפי EnvironmentId) — לא רק הסתרה ב-UI, כדי שלא יהיה ניתן "לדלוף" נתונים בין סביבות גם בטעות תכנותית עתידית.
- **Secrets:** connection strings ו-API keys ב-User Secrets (dev) / משתני סביבה (ריצה) — לעולם לא בקוד/ב-git.

## 10. UI (Blazor Server)

דפים עיקריים ל-V1: ניהול מבנה אפליקציה (Applications/Modules/.../Operations, Environments/Deployments), חיפוש/סינון אירועים, Timeline, Exceptions (קבוצות + סטטיסטיקה), **What's Unusual** (רשימת Findings עם Fact/Observation/Hypothesis מתויגים) עם Drill-Down לאירועים/Timeline/Exceptions/Deployments הקשורים. **וידאוט מלא של מסכים ומצבים** הוא תוצר נפרד (UI Design, תוצר 8).

**למה Blazor Server ולא WebAssembly:** אין צורך ב-offline/client-heavy; Blazor Server פשוט יותר לאימות (session בצד שרת, לא token juggling), ומתאים לכלי פנימי/R&D בקנה מידה כזה.

## 11. Deployment Model

V1 רץ **מקומית**: `dotnet run` / IIS מקומי, SQL Server מקומי (Developer/Express edition מספיק). **החלטה מפורשת:** אריזת Docker/Compose לצורך self-hosting אמיתי נדחית ל-V2 — היא לא מוסיפה ערך להוכחת-היתכנות מול נתוני סימולציה, ותיבחן מחדש כשיהיה יעד deployment אמיתי.

## 12. מבנה פתרון (Solution Structure)

```
LogsPlatform.sln
├── src/
│   ├── LogsPlatform.Domain/            # ישויות + interfaces, ללא תלויות חיצוניות
│   ├── LogsPlatform.Infrastructure/    # EF Core, migrations, repositories
│   ├── LogsPlatform.Analysis/          # Baseline + גלאי אנומליה/קורלציה + בניית Findings
│   ├── LogsPlatform.Web/               # API controllers + Blazor UI + BackgroundService
│   └── LogsPlatform.Client/            # .NET client + Serilog sink adapter
└── tests/
    ├── LogsPlatform.Tests/             # יחידה/אינטגרציה
    └── SyntheticDataGenerator/         # מחולל נתוני סימולציה (2 apps, 6 תרחישים)
```

## 13. סיכונים וידועים-מראש של הבחירה הארכיטקטונית

- **Single point of failure:** תהליך אחד = אם הוא נופל, גם ה-ingestion וגם ה-UI נופלים יחד. מקובל ל-V1/R&D; לא מקובל ל-production אמיתי בלי בדיקה מחדש.
- **Analysis Engine חולק משאבים עם ה-Web process:** ריצה כבדה של הניתוח יכולה להאט זמנית את ה-API/UI באותו תהליך. מרוכך ע"י תזמון (לא רץ ברציפות) ותכנון ה-Analysis כרכיב מבודד שניתן להוציא לתהליך נפרד בעתיד ללא שינוי סכימה.
- **SQL Server כמנוע לוגים:** יעבוד היטב בנפח V1; **לא** נבדק/מתוכנן ל-scale גדול — נקודת הערכה-מחדש מפורשת ל-V2 אם תיכנס אפליקציה אמיתית עם נפח משמעותי.
- **בלי RBAC/Audit מלא:** מקובל לכלי פנימי/R&D יחיד-משתמש; לא מתאים כברירת מחדל ל-multi-user production.

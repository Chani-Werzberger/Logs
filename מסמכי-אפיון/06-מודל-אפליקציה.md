# Application Model

**חלק מ:** אפיון פרויקט R&D — מערכת גנרית לניהול, חקירה ואבחון לוגים
**שלב:** תוצר מס' 6 מתוך 12 בסעיף 23 של האפיון המקורי
**תאריך:** 2026-08-17
**מבוסס על:** [05-מודל-נתונים.md](05-מודל-נתונים.md) (הסכימה), [03-הגדרת-V1.md](03-הגדרת-V1.md) (דרישת 2 אפליקציות סימולציה)

מסמך זה עוסק ב**סמנטיקה והתנהגות** של ההיררכיה — לא בטבלאות עצמן (אלה ב-Data Model) ולא ב-UI (זה בתוצר הבא). המטרה: שני מפתחים שונים שיקראו את זה יגיעו לאותה הבנה של "מה מותר, מה קורה כששם משתנה, ואיך נראית אפליקציה אמיתית במודל הזה".

## 1. כללי ההיררכיה

```
Application (1) ── (0..n) Module ── (0..n) ScreenService ── (0..n) ProcessNode ── (0..n) Operation
```

- **עומק קבוע, לא רקורסיבי.** בניגוד ל-OpenTelemetry (שתי רמות בלבד: `service.namespace`+`service.name`) או ל-Application Insights Application Map (טופולוגיה מתגלה-אוטומטית, לא נשלטת-משתמש), כאן יש בדיוק 5 שכבות קבועות — זו ההחלטה שממנה נגזרת ה-genericity: כל אפליקציה, לא משנה כמה שונה תחומית, ממופה לאותן 5 שכבות.
- **כל שכבה אופציונלית לרוב** — Event יכול לצטט Module בלבד, בלי לרדת ל-Operation (למשל: לוג תשתיתי כללי). אבל לא ניתן לצטט Operation בלי שהוא שייך ל-ProcessNode תקין וכן הלאה — השרשרת חייבת להיות עקבית מלמעלה למטה, לא "לדלג" שכבה.
- **ייחודיות שם:** שם ייחודי בתוך ה-scope המיידי שלו (Module ייחודי בתוך Application, ScreenService ייחודי בתוך Module, וכך הלאה) — לא ייחודיות גלובלית. שני Modules באפליקציות שונות יכולים להיקרא "Payments" בלי התנגשות.
- **Environment ו-Customer/AppUser אינם חלק מהשרשרת ההיררכית** — הם ממדים אורתוגונליים על אותה Application (כל Environment/Customer שייך ישירות ל-Application, לא למקום מסוים בהיררכיה).

## 2. Deployment / Version — איך זה מתחבר להיררכיה

`Deployment` ו-`Version` **לא** תלויים בהיררכיה הפנימית (Module/Operation) — הם ברמת Application+Environment בלבד. הרעיון: גרסה היא "תמונת מצב" של האפליקציה כולה, לא של Module בודד. אם בעתיד יידרש deploy עצמאי של Module בודד (למשל בארכיטקטורת microservices), זו הרחבה עתידית מפורשת — לא נתמכת ב-V1.

## 3. שינויים במבנה לאורך זמן (סעיף 15 באפיון המקורי — "בלי שינוי קוד")

| פעולה | מותר? | מה קורה בפועל |
|---|---|---|
| שינוי שם (Rename) node כלשהו | ✅ | ה-`Id` לא משתנה. Events היסטוריים שמצביעים על אותו `Id` ממשיכים להיות מיוחסים נכון — ה-UI תמיד מציג את השם *הנוכחי*, גם לאירועים ישנים. |
| הוספת node חדש | ✅ | חופשי בכל עת, לא משפיע על נתונים קיימים. |
| **מחיקת** node שיש לו Events היסטוריים | ❌ אסור | נמנע ע"י `IsActive=false` (soft-delete) בלבד — ראו [05-מודל-נתונים.md](05-מודל-נתונים.md) סעיף 2. Node לא-פעיל נעלם מרשימות הבחירה ב-Ingestion/Admin, אבל היסטוריית האירועים שלו נשארת שלמה וניתנת-לחקירה. |
| מחיקת node **בלי** Events היסטוריים | ✅ hard-delete | מותר — לא מייצר יתומים. |
| הזזת node לאב אחר (למשל ScreenService עובר בין Modules) | 🟡 מותר, בזהירות | טכנית מותר (רק שינוי FK), אבל משנה את המשמעות ההיסטורית של אירועים ישנים (הם "יעברו" למודול החדש רטרואקטיבית ב-UI). מומלץ לתעד כפעולת אדמין מפורשת, לא feature נסתר. |

## 4. שתי האפליקציות הסימולציות של V1

נדרשות לפי [03-הגדרת-V1.md](03-הגדרת-V1.md) כדי להוכיח גנריות. נבחרו במתכוון משני תחומים שונים לגמרי (לא וריאציה על אותה דוגמה) — וישמשו גם את ה-Synthetic Data Generator (תוצר Test Strategy) לצורך 6 תרחישי הבדיקה.

### RetailPulse (מסחר אלקטרוני)

```
RetailPulse
├── Orders (Module)
│   └── OrderApiService (Service)
│       ├── CreateOrder (Process)
│       │   ├── ValidateCart (Operation)
│       │   ├── ReserveStock (Operation)
│       │   ├── ChargePayment (Operation)
│       │   └── ConfirmOrder (Operation)
│       └── CancelOrder (Process)
├── Payments (Module)
│   └── PaymentGateway (Service)
│       └── ProcessPayment (Process)
│           ├── AuthorizeCard (Operation)
│           └── CaptureCharge (Operation)
└── Inventory (Module)
    └── StockService (Service)
        └── StockSync (Process)
            ├── PullSupplierFeed (Operation)
            └── UpdateStockLevels (Operation)
```

### FieldOps (ניהול צוותי שטח)

```
FieldOps
├── Scheduling (Module)
│   ├── DispatchBoard (Screen)
│   └── SchedulerApi (Service)
│       └── AssignTechnician (Process)
│           ├── MatchAvailability (Operation)
│           └── SendNotification (Operation)
└── Reporting (Module)
    └── DailyReport (Screen)
        └── GenerateReport (Process)
            ├── AggregateJobs (Operation)
            └── RenderPdf (Operation)
```

### מיפוי לתרחישי הבדיקה (6 התרחישים מ-[03-הגדרת-V1.md](03-הגדרת-V1.md) סעיף 4)

| תרחיש | אפליקציה | מיקום |
|---|---|---|
| Error Spike | RetailPulse | `ChargePayment` מתחיל להיכשל בקצב חריג |
| Performance Degradation | FieldOps | `MatchAvailability` — משך הפעולה עולה הדרגתית |
| New Exception | RetailPulse | `ReserveStock` זורק exception type שלא נראה מעולם |
| Deployment-Related Anomaly | FieldOps | Deployment לגרסה חדשה ב-Production, ואז `AggregateJobs` מתחיל לשגות |
| Missing Activity | RetailPulse | `PullSupplierFeed` (רץ בד"כ כל שעה) מפסיק לדווח פעילות |
| Customer-Specific Anomaly | RetailPulse | Customer בודד מייצר דפוס חריג (למשל שיעור refund גבוה) בעוד שאר הלקוחות תקינים |

זו הדוגמה הקנונית — Test Strategy (תוצר הבא בסדרה שאחרי Analysis/Ingestion/UI/Security Design) יבנה עליה ישירות.

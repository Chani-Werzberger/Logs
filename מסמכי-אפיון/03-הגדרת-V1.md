## 1. הנחות עבודה שקבעו את גבולות V1

| פרמטר | החלטה |
|---|---|
| פיילוט | **גנרי בלבד** — ללא חיבור לאפליקציה אמיתית (כולל Inova). נבדק מול נתוני סימולציה/synthetic data. |
| היקף אבחון | Baseline + Anomaly Detection **ברמה פשוטה** נכנסים ל-V1 (לא נדחים ל-V2) — כולל מודל Fact/Observation/Hypothesis. |
| Tech stack | **.NET** ל-Backend, בהתאם להקשר Inova/Serilog שכבר נחקר. |
| Multi-app | **לפחות 2 Applications סימולציות מלאות במקביל**, כדי להוכיח שהמודל גנרי באמת. |
| כוח אדם/זמן | פיתוח **עצמאי, עם Claude**, שבועות עד חודשים בודדים — לא צוות, לא לוח זמנים ארוך. |
| UI | **UI בסיסי נכלל ב-V1** (לא רק API) — כי הערך המרכזי הוא חוויית החקירה. |

## 2. מטרת V1 (Success Criteria)

לפי סעיף 17 באפיון המקורי, V1 צריך להוכיח את השרשרת המלאה:

> קל לחבר Application → קל לקלוט לוגים → קל לחפש ולחקור → קל להבין את ההקשר → **המערכת בעצמה מזהה ומסבירה דברים חריגים**.

V1 נחשב למוצלח אם, מול 2 אפליקציות סימולציות עם נתוני לוג מסונתזים:
1. ניתן להגדיר את המבנה הלוגי המלא של כל אפליקציה (5 שכבות) דרך UI, ללא שינוי קוד.
2. לוגים structured נקלטים דרך API/client, כולל Correlation ID/Trace ID.
3. ניתן לחפש, לסנן, ולעבור מאירוע בודד ל-Timeline המלא שלו.
4. Exceptions מקובצים אוטומטית עם סטטיסטיקת הופעה.
5. **המערכת מזהה בעצמה**, ללא שאילתה ידנית, את 6 תרחישי החריגה המדומים (סעיף 8 למטה) ומציגה אותם כ-Findings.
6. כל Finding מציג בבירור מה Fact, מה Observation, ומה עדיין Hypothesis שלא הוכח — ומאפשר Drill Down מלא לראיות.

## 3. תחומי סקופ — טבלת מיפוי מלאה

| תחום (לפי אפיון מקורי) | סטטוס ב-V1 | הערות |
|---|---|---|
| ניהול מבנה Application (סעיף 4, 15) | ✅ **מלא** | 5 שכבות (App→Module→Screen/Service→Process→Operation), Environments/Versions/Deployments, אדמין דרך UI |
| Ingestion (סעיף 5) | ✅ **מצומצם** | HTTP API קנייני + client פשוט ל-.NET (Serilog sink adapter). **OTLP נדחה ל-V2** — אך שמות שדות ה-Severity/Service ייבנו תואמים-מראש למוסכמות OpenTelemetry |
| חיפוש וחקירה (סעיף 6) | ✅ **מלא** | סינון רב-ממדי בסיסי |
| Timeline (סעיף 7) | ✅ **מלא** | לפי Request/Operation/Correlation ID/User/Customer |
| ניהול Exceptions (סעיף 8) | ✅ **מצומצם** | קיבוץ לפי fingerprint פשוט (stack-trace + exception-type + message-template hash), לא ML סמנטי כמו Sentry |
| Deployment Awareness (סעיף 9) | ✅ **מצומצם** | סימון Deployment + קורלציה סטטיסטית פשוטה ל-Error Spike; לא היסק סיבתי מתוחכם |
| מנגנון אבחון עצמאי — What's Unusual (סעיף 10) | ✅ **מצומצם** | מבוסס Baseline פשוט (ממוצע+סטיית-תקן, bucketing לפי שעה-ביום) — לא seasonality מתוחכם |
| Correlation Analysis (סעיף 11) | ✅ **4 סוגים נבחרים** | Deployment→Error Spike; Missing Activity; חריגת Customer/Tenant; Exception→כשל מאוחר ב-workflow (דרך Correlation ID) |
| Baseline (סעיף 12) | ✅ **מצומצם** | היסטוריה + ממוצע/סטיית-תקן + bucketing שעה-ביום. **לא** seasonality decomposition/ML |
| תצוגת Findings — What's Unusual (סעיף 13) | ✅ **מלא** | כולל תיוג מפורש Fact/Observation/Hypothesis/Conclusion — זהו הרכיב הכי חשוב ב-V1 |
| Drill Down (סעיף 14) | ✅ **מלא** | מ-Finding לאירועים/Timeline/Exceptions/Operations/Deployments |
| אבטחה (סעיף 16) | 🟡 **מינימלי** | אותנטיקציה פשוטה (משתמש אדמין/API key) + הפרדת Environments ברמת מודל הנתונים. **בלי** RBAC גרנולרי, בלי Audit log מלא. Secrets בקונפיגורציה/env בלבד — לא בקוד |
| Dashboards כלליים | ❌ **בחוץ** | לא מטרת המוצר (סעיף 17 באפיון המקורי) |
| SDK לשפות נוספות | ❌ **בחוץ** | .NET בלבד ב-V1 |
| מדיניות שמירה/ארכוב לוגים | ❌ **בחוץ** | ידוע כפער — יתועד ב-Known Limitations |

## 4. תרחישי בדיקה — נתוני סימולציה (חובה, לפי סעיף 21 באפיון המקורי)

V1 חייב לכלול מחוללי נתונים סינתטיים שיוצרים בכוונה, על פני 2 האפליקציות הסימולציות:

1. **Error Spike** — עלייה חריגה בכמות שגיאות ב-Operation ספציפי.
2. **Performance Degradation** — עלייה הדרגתית/פתאומית במשך פעולה (Duration) ביחס ל-baseline.
3. **New Exception** — Exception שלא נראה מעולם באפליקציה.
4. **Deployment-Related Anomaly** — חריגה (בשגיאות/ביצועים) שמתחילה זמן קצר אחרי Deployment מדומה.
5. **Missing Activity** — Operation שפעילותו יורדת/נעלמת בפתאומיות.
6. **Customer-Specific Anomaly** — דפוס חריג המשויך ל-Customer/Tenant ספציפי, בעוד שאר הלקוחות תקינים.

**קריטריון קבלה:** עבור כל אחד מ-6 התרחישים, המערכת חייבת לייצר Finding מתאים באופן עצמאי (ללא שאילתה ידנית), עם Fact/Observation ברורים ו-Hypothesis (אם רלוונטי) מסומן ככזה ולא כמסקנה.

## 5. מה בחוץ — ולמה (מפורש)

- **OTLP/OpenTelemetry native ingestion** — נדחה כי המחקר הראה שהדרך הנכונה (Collector+adapter) היא עבודה נוספת משמעותית מעבר ל-API הקנייני; שדות ה-V1 ייבנו תואמים-מראש כדי לא לסגור דלת.
- **RBAC/Audit מלאים** — לא ריאלי לפיתוח עצמאי בטווח הזמן; V1 מסתפק בבידוד Environment + אותנטיקציה בסיסית.
- **Baseline מתוחכם (ML/seasonality)** — App Insights ו-Sentry כבר עושים את זה טוב ברמה שקשה להתחרות בה עצמאית; V1 מוכיח את העיקרון (הפרדת Fact/Hypothesis, לא את התחכום הסטטיסטי) ומצהיר על כך בגלוי במוצר עצמו.
- **חיבור אמיתי לאפליקציה** — נדחה במפורש לפי החלטת בעלת הפרויקט; V1 מוכיח גנריות מול 2 סימולציות, לא מול production אמיתי.
- **Dashboards כלליים, SDK רב-שפתי, מדיניות ארכוב** — מחוץ ל-value proposition של V1 (סעיף 17 באפיון המקורי).

## 6. סיכון היקף וסדר עדיפויות לצמצום

ה-scope שנבחר (5 שכבות היררכיה + 4 סוגי Correlation + Baseline + Findings, הכל בפיתוח עצמאי של שבועות-חודשים) שאפתני. אם באמצע המימוש יתברר שההיקף גדול מדי, **סדר הצמצום המומלץ** (מהראשון-לוותר-עליו ועד האחרון):

1. **לצמצם קודם את מספר סוגי ה-Correlation Analysis** — להתחיל מ-2 (Deployment→Error Spike, Missing Activity) ולדחות את השניים הנוספים (Customer-specific, Exception→downstream) ל-V1.1.
2. **לצמצם עומק Exception Grouping** — fingerprint גס יותר (רק exception-type, בלי stack-trace hashing) אם צריך.
3. **לא לוותר** על העומק ההיררכי המלא (5 שכבות) או על מודל Fact/Observation/Hypothesis/Conclusion — אלה שני עמודי התווך שהמחקר זיהה כהבדלה התחרותית האמיתית ([02-פער-שוק.md](01-מחקר-כלים-קיימים/02-פער-שוק.md)); ויתור עליהם הופך את V1 ל"עוד כלי לוגים" ללא ייחוד.

## 7. מה הלאה

לפי סעיף 23 באפיון המקורי, השלבים הבאים אחרי אישור מסמך זה: **Architecture** (עם חלופות מנומקות), **Data Model** (כולל ה-Application Model ההיררכי), **Application Model**, **Ingestion/API Design**, **Analysis/Anomaly Detection Design**, **UI Design**, **Security Design**, **Test Strategy**, **תוכנית עבודה ואבני דרך**. אין להתחיל פיתוח קוד משמעותי לפני שאלה נבדקים ומאושרים.

# אפיון המוצר

**חלק מ:** אפיון פרויקט R&D — מערכת גנרית לניהול, חקירה ואבחון לוגים
**שלב:** תוצר מס' 2 מתוך 12 בסעיף 23 של האפיון המקורי
**תאריך:** 2026-08-17
**מבוסס על:** האפיון המקורי (הדרישות מטעם הלקוח, 25 סעיפים) + [מחקר הכלים הקיימים](01-מחקר-כלים-קיימים/) (מאומת מול תיעוד רשמי)

## 1. חזון ומטרה

מערכת גנרית לניהול, חקירה ואבחון לוגים ממערכות תוכנה שונות, שאינה מסתפקת באיסוף והצגה של לוגים אלא **מכירה את המבנה הלוגי של האפליקציה** (Application → Module → Screen/Service → Process → Operation), מקשרת אירועים להקשר הזה, ומפעילה מנגנון אבחון עצמאי שמזהה חריגות, מגמות ושילובים חשודים בין אירועים — תוך הפרדה נוקשה בין מה שנמדד (**Fact**), מה שנצפה כחריגה (**Observation**), הסבר אפשרי שטרם הוכח (**Hypothesis**), ומסקנה שאושרה בראיות (**Conclusion**).

המוצר **אינו** שואף להחליף Grafana, ELK, Seq, Application Insights, APM מלא או SIEM. לפי מחקר השוק (ראו [02-פער-שוק.md](01-מחקר-כלים-קיימים/02-פער-שוק.md)), התחומים האלה מכוסים היטב ואף אחד מהם — כולל App Insights ו-Sentry, המתקדמים ביותר בתחום ה-anomaly detection האוטומטי — לא ממש את השילוב הספציפי שהמוצר הזה בנוי סביבו.

## 2. מיצוב תחרותי (מעודכן לאחר המחקר)

המחקר גילה שהנחת-היסוד הראשונית ("אף כלי לא עושה Application Awareness + Baseline + Anomaly Detection") נכונה רק בחלקה. לכן המיצוב הבא **אינו** "אנחנו מזהים חריגות ומבינים את מבנה האפליקציה" (זה כבר קיים, טוב, ב-Application Insights ו-Sentry) — אלא שילוב ספציפי של ארבעה עקרונות שאף כלי לא ממש יחד:

1. **מודל אפליקציה גנרי, עמוק, נשלט-משתמש** (Application→Module→Screen/Service→Process→Operation) — לא namespace+name שטוח (OpenTelemetry), לא טופולוגיה מתגלה-אוטומטית (Application Insights Application Map), לא properties חופשיים ללא סמנטיקה (Seq/Loki).
2. **הפרדה מוצרית מפורשת בין Fact / Observation / Hypothesis / Conclusion** בכל ממצא — אף מתחרה, כולל שכבות ה-AI המתקדמות (Sentry Seer, Azure Copilot Observability Agent), לא חושף למשתמש הפרדה שקופה כזו בין מה שהוכח למה שעדיין ניחוש.
3. **עצמאות מספק/ענן** — היכולות המתקדמות ביותר בשוק כלואות מאחורי Azure (Smart Detection, Copilot Agent) או Grafana Cloud Enterprise. מוצר self-hosted, לא תלוי-ענן, עם יכולת baseline+anomaly detection שקולה.
4. **"Finding" כמושג-על עצמאי** שיכול להיווצר מכל שילוב אירועים חשוד — לא רק exception spike — עם Drill Down שתמיד חוזר לראיות מכמה מקורות בו-זמנית, ולא מעוגן לישות טבעית אחת של הכלי (Issue/Transaction/Trace).

## 3. משתמשי היעד

**משתמש ראשי: מפתח/ת שמאבחנת בעיה בפרודקשן או בסביבת בדיקות.** דמות דומה למי שהיום היה פותח Seq/Sentry ומתחיל לחפש — אך במוצר הזה, השאלה הראשונה שהמוצר עונה עליה בעצמו היא "מה חריג כרגע ולמה", לא רק "מה קרה כשאני שואל/ת".

משתמשים משניים (לא בליבת V1, אבל רלוונטיים לתכנון ה-Application Model): מנהל/ת מוצר שמגדיר/ה את מבנה האפליקציה החדשה שמתחברת למערכת; Support/DevOps שמנטרים בריאות מערכת.

## 4. עקרונות ליבה (מהאפיון המקורי, ללא שינוי)

- **מוצר גנרי** — לא נבנה עבור אפליקציה ספציפית אחת; חייב לתמוך בחיבור אפליקציות מרובות, כל אחת עם המבנה הלוגי שלה.
- **Application Awareness** — לוגים תמיד מוצגים בהקשר ההיררכי של האפליקציה שבה קרו.
- **עובדות מול מסקנות** — Fact / Observation / Hypothesis / Conclusion. אין להציג השערה כ-root cause ללא הוכחה, בשום מסך ובשום שלב.

## 5. מפת יכולות המוצר המלא (טווח ארוך — לא V1)

זהו תיאור המוצר בשלמותו, כפי שהאפיון המקורי מגדיר אותו (סעיפים 4–16). חלוקת מה נכנס ל-V1 מול מה נדחה מפורטת במסמך [03-הגדרת-V1.md](03-הגדרת-V1.md) הנפרד.

| תחום | תיאור קצר | סעיף באפיון המקורי |
|---|---|---|
| ניהול מבנה Application | הגדרת Applications, סביבות, גרסאות, Deployments, Modules, Screens, Services, Processes, Operations, מקורות לוגים, Customers/Tenants — ללא שינוי קוד | 4, 15 |
| Ingestion | API + SDK/Client לקליטת Structured Logs, עם חוזה שדות ברור (Timestamp, Severity, Application, Environment, Version, Deployment, User, Customer, Module, Screen/Service, Process, Operation, Correlation ID, Trace ID, Duration, Exception, Stack Trace, Metadata חופשי) | 5 |
| חיפוש וחקירה | סינון רב-ממדי, מעבר מאירוע בודד להקשר הרחב שלו | 6 |
| Timeline | רצף אירועים לפי Request/Operation/Correlation ID/User/Customer/תהליך | 7 |
| ניהול Exceptions | קיבוץ Exceptions דומים, סטטיסטיקות הופעה, מגמה | 8 |
| Deployment Awareness | קשר בין Deployment→Version→Events→Exceptions→Performance, מוצג כהשערה עד שמוכח | 9 |
| מנגנון אבחון עצמאי (What's Unusual) | זיהוי חריגות: Exception חדש, קפיצות בכמות/משך, ירידת/עליית פעילות, דפוסי משתמש/Customer חריגים, שילובי אירועים חשודים | 10 |
| Correlation Analysis | זיהוי קשרים בין אירועים ממקורות שונים, עם הצגת הראיות | 11 |
| Baseline | למידת התנהגות רגילה הדרגתית, הבחנה בין חריגה אמיתית לתנודה מוכרת | 12 |
| תצוגת Findings | לכל Finding: What/When/Where/Severity/Confidence/Evidence/Related Events/Exceptions/Deployments/Possible Explanation + תיוג Fact/Observation/Hypothesis | 13 |
| Drill Down | מ-Finding אל האירועים המקוריים, Timeline, Exceptions, Operations, Users, Customers, Deployments, Versions, ממצאים קשורים | 14 |
| ממשק ניהול מבנה אפליקציה | הוספה/שינוי/ארגון מבנה לוגי ללא שינוי קוד | 15 |
| אבטחה | Authentication, Authorization, הפרדת Applications/Environments, הגנה על מידע רגיש, Secrets, Audit, מדיניות שמירה/ארכוב | 16 |

## 6. מה המוצר לא (ואסור שיהפוך להיות)

- לא תחליף ל-Grafana/ELK/Seq/Application Insights/APM מלא/SIEM (סעיף 17 באפיון המקורי; אושש גם במחקר השוק).
- לא כלי Dashboarding/Visualization כללי — זו חוזקת Grafana, לא הכיוון שלנו.
- לא מנוע ML מתוחכם שמתחרה ב-Dynamic Thresholds של Azure או Matrix-Profile/Prophet של Sentry — ה-Baseline שלנו פשוט ומוצהר ככזה, לא מתחזה לתחכום שאין.
- לא מציג לעולם השערה כמסקנה מוכחת — זהו קו אדום מוצרי, לא רק עיצובי.

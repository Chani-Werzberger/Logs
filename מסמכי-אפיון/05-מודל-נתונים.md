# Data Model

**חלק מ:** אפיון פרויקט R&D — מערכת גנרית לניהול, חקירה ואבחון לוגים
**שלב:** תוצר מס' 5 מתוך 12 בסעיף 23 של האפיון המקורי
**תאריך:** 2026-08-17
**מבוסס על:** [04-ארכיטקטורה.md](04-ארכיטקטורה.md) (SQL Server, גישה יחסית + JSON למטא-דאטה חופשי)

## 1. עקרונות מנחים

- **ההיררכיה היא ישויות ראשונות-מעמד**, לא properties חופשיים — זו ההבדלה התחרותית המרכזית (ראו [02-אפיון-המוצר.md](02-אפיון-המוצר.md)).
- **Event מדנרמל (denormalized) כלפי מעלה בהיררכיה** — מאחסן ישירות FK לכל שכבה שהאירוע ציין (ModuleId/ScreenServiceId/ProcessId/OperationId), מיושב ע"י ה-Ingestion API בזמן קליטה. זה נמנע מ-joins מרובי-hop בשאילתות סינון נפוצות, במחיר קצת redundancy באחסון — trade-off סביר לטבלה שהיא ברובה read/filter-heavy.
- **Fact/Observation/Hypothesis/Conclusion מקבל טבלה משלו** (`FindingStatement`), לא שדה טקסט חופשי — כדי שההפרדה האפיסטמית תיאכף במבנה הנתונים עצמו, לא רק במוסכמת UI.
- **מפתחות:** `bigint IDENTITY` לטבלת Events (נפח גבוה, יתרון clustering של מפתח עולה-רציף); `int IDENTITY` לטבלאות היררכיה/הפניה (נפח נמוך, קריא לבני-אדם באדמין).

## 2. ישויות ליבה — מבנה אפליקציה

```
Application (Id, Name, Description, CreatedAt)
Environment (Id, ApplicationId→Application, Name, IsProduction bit)
Version (Id, ApplicationId→Application, VersionNumber, ReleaseNotes, CreatedAt)
Deployment (Id, ApplicationId→Application, EnvironmentId→Environment, VersionId→Version, DeployedAt, Notes)
Module (Id, ApplicationId→Application, Name, Description, IsActive bit)
ScreenService (Id, ModuleId→Module, Name, Type [Screen|Service], Description, IsActive bit)
ProcessNode (Id, ScreenServiceId→ScreenService, Name, Description, IsActive bit)
Operation (Id, ProcessId→ProcessNode, Name, Description, IsActive bit)
Customer (Id, ApplicationId→Application, ExternalCustomerId, Name)
AppUser (Id, ApplicationId→Application, ExternalUserId, DisplayName)
LogSource (Id, ApplicationId→Application, Name, Description)
ApiKey (Id, ApplicationId→Application, KeyHash, Label, CreatedAt, RevokedAt NULL)
```

הערות:
- `ProcessNode` (לא `Process`) — נמנע מהתנגשות שם עם מושג "OS process".
- `ScreenService.Type` הוא discriminator (Screen/Service) על ישות אחת — תואם את סימון "Screen / Service" בדוגמת האפיון המקורי, ולא שתי טבלאות נפרדות עם אותה סמנטיקה בדיוק.
- `IsActive` על 4 טבלאות ההיררכיה (Module/ScreenService/ProcessNode/Operation) מאפשר **soft-delete בלבד**: node שכבר יש לו Events היסטוריים לעולם לא נמחק hard-delete (זה ימחק/יתום היסטוריה), רק מסומן לא-פעיל. פירוט מלא בסעיף 3 של [06-מודל-אפליקציה.md](06-מודל-אפליקציה.md).
- `ApiKey` הוא per-Application (לא per-LogSource) ב-V1, כפי שנקבע בארכיטקטורה. `LogSource` הוא ישות תיאורית בלבד (סעיף 4 באפיון) — לא מנגנון auth.
- `Deployment` **לא** מקושר ישירות מ-`Event` — הקורלציה (Deployment→Error Spike) נעשית ע"י Analysis Engine שמצליב `(EnvironmentId, VersionId, Timestamp)` על אירועים מול `(EnvironmentId, VersionId, DeployedAt)` על Deployments. זה משאיר את `Event` פשוט (הוא כבר יודע את הגרסה שלו בזמן אמת, בלי תלות בטבלת Deployment).

## 3. Events — הטבלה המרכזית

```
Event (
  Id bigint IDENTITY PK,
  Timestamp datetime2,
  Severity int,                      -- ממופה למודל OTel: TRACE(1-4)/DEBUG(5-8)/INFO(9-12)/WARN(13-16)/ERROR(17-20)/FATAL(21-24)
  ApplicationId int → Application,
  EnvironmentId int → Environment,
  VersionId int NULL → Version,
  ModuleId int NULL → Module,
  ScreenServiceId int NULL → ScreenService,
  ProcessId int NULL → ProcessNode,
  OperationId int NULL → Operation,
  CustomerId int NULL → Customer,
  AppUserId int NULL → AppUser,
  CorrelationId nvarchar(100) NULL,
  TraceId nvarchar(100) NULL,
  SpanId nvarchar(100) NULL,
  ParentSpanId nvarchar(100) NULL,
  DurationMs float NULL,
  Message nvarchar(max),
  MessageTemplate nvarchar(1000) NULL,
  ExceptionGroupId bigint NULL → ExceptionGroup,
  StackTrace nvarchar(max) NULL,
  MetadataJson nvarchar(max) NULL     -- JSON חופשי, לא מאונדקס בשלמותו
)
```

**אינדקסים מרכזיים:** `(ApplicationId, EnvironmentId, Timestamp)`, `(ApplicationId, OperationId, Timestamp)`, `(CorrelationId)`, `(TraceId)`, `(ExceptionGroupId)`, full-text index על `Message`. הכלל המנחה: כל שדה שמופיע כממד סינון בסעיף 6 באפיון המקורי (טווח זמן, Application, Environment, Severity, Module, Screen, Service, Operation, User, Customer, Exception, Version, Correlation ID, Duration) — ממודד.

**בידוד Environment (מסעיף 9 בארכיטקטורה):** נאכף בכך שכל שאילתה חייבת לכלול `EnvironmentId` בתנאי ה-WHERE ברמת ה-repository — לא רק אינדקס, אלא חוזה קוד.

## 4. Exceptions ו-Baseline

```
ExceptionGroup (
  Id bigint IDENTITY PK,
  ApplicationId int → Application,
  Fingerprint nvarchar(200),          -- hash של (ExceptionType + StackTrace-signature + MessageTemplate)
  ExceptionType nvarchar(500),
  MessageTemplate nvarchar(1000),
  RepresentativeStackTrace nvarchar(max),
  FirstSeenAt datetime2,
  LastSeenAt datetime2,
  OccurrenceCount int                 -- מתעדכן ע"י Analysis Engine, לא בזמן-אמת על כל insert
)

Baseline (
  Id bigint IDENTITY PK,
  ApplicationId int → Application,
  ScopeType int,                      -- Operation | ExceptionGroup
  ScopeId bigint,                     -- OperationId או ExceptionGroupId, לפי ScopeType (לא FK אכיף — ראו סעיף 6)
  MetricType int,                     -- EventCount | ExceptionCount | DurationMs
  BucketHourOfDay tinyint,            -- 0–23, bucketing פשוט כפי שנקבע ל-V1 (לא seasonality מתוחכם)
  MeanValue float,
  StdDevValue float,
  SampleCount int,
  LastUpdatedAt datetime2
)
```

`ExceptionGroup.Fingerprint` הוא ה-grouping הפשוט שנקבע ב-[03-הגדרת-V1.md](03-הגדרת-V1.md) (stack-trace+type+message-template hash) — לא ML סמנטי כמו Sentry. `OccurrenceCount`/`LastSeenAt` מתעדכנים בריצת ה-Analysis Engine, לא בכל insert בודד (נמנע מ-contention על שורת ה-group בנפח כתיבה גבוה).

## 5. Findings — הליבה של "What's Unusual"

```
Finding (
  Id bigint IDENTITY PK,
  ApplicationId int → Application,
  Type int,                           -- ErrorSpike | MissingActivity | CustomerAnomaly | DeploymentCorrelation | DownstreamFailure
  Title nvarchar(500),
  DetectedAt datetime2,
  Severity int,
  ConfidenceLevel int,                 -- Low | Medium | High — לא אחוז מדומה-מדויק
  Status int                          -- New | Acknowledged | Resolved | Dismissed
)

FindingStatement (
  Id bigint IDENTITY PK,
  FindingId bigint → Finding,
  Kind int,                           -- Fact | Observation | Hypothesis | Conclusion
  Text nvarchar(2000),
  OrderIndex int
)

Evidence (
  Id bigint IDENTITY PK,
  FindingId bigint → Finding,
  EvidenceType int,                   -- Event | ExceptionGroup | Deployment | Baseline | Operation
  ReferenceId bigint,                 -- מפתח לתוך הטבלה המתאימה ל-EvidenceType (polymorphic — ראו סעיף 6)
  Description nvarchar(1000)
)
```

**זהו החלק הכי חשוב בסכימה כולה.** כל Finding הוא לא שדה טקסט חופשי — הוא אוסף `FindingStatement` מסודר, כל אחד מתויג במפורש כ-Fact/Observation/Hypothesis/Conclusion, עם `Evidence` שמצביע חזרה על הנתונים הגולמיים שתומכים בו. ה-UI (What's Unusual, Drill-Down) בנוי ישירות מעל שתי הטבלאות האלה.

## 6. Trade-off מפורש: Evidence הוא Polymorphic FK

`Evidence.ReferenceId` לא אוכף FK constraint ברמת ה-DB (כי `EvidenceType` קובע לאיזו טבלה `ReferenceId` מצביע — Event, ExceptionGroup, Deployment, Baseline או Operation). זו סטייה מודעת מ-referential integrity מלאה, במחיר: תקינות הקישור נאכפת ברמת קוד האפליקציה (ב-`LogsPlatform.Analysis`, היחיד שכותב ל-Evidence) ולא ע"י SQL Server. **חלופה שנשקלה ונדחתה:** טבלת קישור נפרדת לכל סוג evidence (`EventEvidence`, `ExceptionEvidence` וכו') עם FK אכיף — נכונה יותר תיאורטית, אבל מכפילה קוד/schema ב-5 טבלאות כמעט-זהות עבור תועלת נמוכה ב-V1 (writer יחיד, לא multi-team). **נקודת הערכה מחדש:** אם ב-V2 ייכתבו ל-Evidence כמה רכיבים שונים (לא רק Analysis Engine), שווה לעבור לחלופה הנכונה יותר.

## 7. תרשים יחסים (מפושט)

```
Application ─┬─ Environment ─── Deployment ─── Version
             ├─ Module ─── ScreenService ─── ProcessNode ─── Operation
             ├─ Customer
             ├─ AppUser
             ├─ LogSource
             ├─ ApiKey
             ├─ Event (FK לכל הנ"ל, לפי הרלוונטי)
             │     └─ ExceptionGroupId → ExceptionGroup
             ├─ ExceptionGroup
             ├─ Baseline (ScopeId → Operation/ExceptionGroup, לא אכיף)
             └─ Finding ─┬─ FindingStatement (Fact/Observation/Hypothesis/Conclusion)
                         └─ Evidence (→ Event/ExceptionGroup/Deployment/Baseline/Operation, לא אכיף)
```

## 8. מה נשאר לתוצרים הבאים

חוזה ה-JSON המדויק של ה-Ingestion API (מיפוי שדות נכנסים ← עמודות Event) הוא חלק מתוצר **Ingestion/API Design** (הבא בתור). לוגיקת הגלאים עצמם (מתי בדיוק Finding נוצר, איך Baseline מתעדכן צעד-אחר-צעד) היא חלק מתוצר **Analysis/Anomaly Detection Design**.

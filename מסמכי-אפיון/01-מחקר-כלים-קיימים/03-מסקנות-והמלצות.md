## החלטות שהתקבלו בעקבות המחקר

### 1. Structured Logs — חובה ✅
כל חמשת הכלים בנויים סביב structured events, לא free-text. אין בכך חידוש, אבל זו נקודת מוצא לא-משתנה. Severity/Level צריך לאמץ את מודל OpenTelemetry (`SeverityText` + `SeverityNumber`, 1–24, TRACE→FATAL) במקום להמציא סקאלה חדשה — זה תקן מאומת, יציב, ומוכר.

### 2. תאימות OpenTelemetry — כן, אך לא כשרת OTLP-מאפס ✅
מומלץ לקבל OTLP כערוץ ingestion, אבל **לא** על ידי מימוש עצמאי מלא של הפרוטוקול. התיעוד הרשמי של OpenTelemetry עצמו ממליץ במרומז על תבנית: להריץ OpenTelemetry Collector כשער-כניסה, עם exporter/adapter מותאם-אישית שממפה את מודל ה-OTel (resource/log/span) לסכימה הפנימית שלנו. זה מצמצם את העבודה ל"כתיבת adapter אחד" במקום מימוש מלא של gRPC+HTTP+protobuf+partial-failure semantics. **החלטה: לתכנן שכבת ingestion שמקבלת גם Structured HTTP API קנייני (למקרה הפשוט/SDK קליל) וגם OTLP דרך Collector-based adapter (למקרה ה-enterprise/existing-instrumentation).**

### 3. Correlation ID + Trace ID — חובה, לפי מודל OTel ✅
כל הכלים המבוססים (Seq מ-2024.1, Sentry, App Insights, OTel עצמו) מתכנסים לאותו מודל: `trace_id` משותף לכל ה-spans של פעולה אחת, `span_id` ייחודי לכל span, `parent_id` להיררכיה, ו-Context Propagation (W3C TraceContext) להעברה בין תהליכים/שירותים. **החלטה: לאמץ את המודל הזה כמות שהוא**, כדי לקבל תאימות "בחינם" עם כל אפליקציה שכבר משתמשת ב-OpenTelemetry, Serilog+Seq, או Sentry SDK.

### 4. מבנה אפליקציה היררכי (Application → Module → Screen/Service → Process → Operation) — רכיב מרכזי וייחודי שלנו ✅
זהו אחד משני ההבדלים החדים ביותר שנמצאו במחקר: **אף כלי לא נותן היררכיה כזו כברירת מחדל**. Seq/Loki שטוחים לגמרי (properties/labels חופשיים בלי סמנטיקה). OpenTelemetry מגדיר רק שתי רמות (`service.namespace` + `service.name`). Application Insights בונה טופולוגיה **אוטומטית** מתוך dependency calls (Application Map) — אבל זו תגלית, לא הגדרה נשלטת-משתמש; Azure-only; ולא תומכת בעומק של 5 רמות. **החלטה: זהו הרכיב שהכי הרבה שווה להשקיע בו בשלב Data Model + Application Model הבא — הוא לא קיים בשום מקום אחר בעומק ובגמישות שהאפיון דורש.**

### 5. Baseline Learning — רכיב מרכזי, אך יש להגדיר scope ריאלי ל-V1 🟡
App Insights (Smart Detection, Dynamic Thresholds) ו-Sentry (Escalating Issues, Metric Anomaly Detection) **כבר עושים baseline learning אמיתי ומאומת** — כולל נטרול seasonality/יום-בשבוע וצמיחה טבעית בשימוש. זה לא רעיון חדש; זה תחום מחקר פעיל אצל ספקים עם צוותי data-science גדולים. **הסתייגות:** אין לתכנן V1 שמנסה "להדביק" את התחכום הסטטיסטי של Dynamic Thresholds (3+ שבועות seasonality מפורש) או Matrix-Profile/Prophet של Sentry. **החלטה: להתחיל מ-baseline פשוט וברור (ממוצע+סטיית-תקן היסטורי, עם חלוקה לפי שעה/יום כברירת מחדל בסיסית), ולתעד מפורשות בכל Finding את רמת הביטחון הסטטיסטי — לא להתחזות לתחכום שאין.**

### 6. Anomaly Detection — רכיב מרכזי, אך לא הערך היחיד ✅
נדרש (סעיף 10 באפיון), אבל **חייב להיות משולב** עם עקרון #7 (הפרדת Fact/Hypothesis) כדי להיות שונה במהות מ-Smart Detection/Escalating Issues, לא רק "עוד גרסה" שלהם. ראו מסמך פער-שוק לניתוח המלא.

### 7. מודל Fact / Observation / Hypothesis / Conclusion — הרכיב הייחודי ביותר שנמצא ✅
זהו הממצא הכי חד של כל המחקר: **אף אחד מחמשת הכלים — כולל Sentry Seer ו-Azure Copilot Observability Agent המתקדמים — לא ממש הפרדה מוצרית מפורשת בין מדידה, תצפית, השערה ומסקנה מוכחת.** כולם מציגים ממצאי AI/ML כאילו הם כבר מסקנה סופית, גם כשמדובר בהסתברות (94.5% דיוק ב-Autofix, לדוגמה) ולא בוודאות. **החלטה: זהו הרכיב שצריך לקבל את מירב תשומת הלב בעיצוב ה-UI וה-Data Model של Findings — הוא ההבדל האמיתי, לא טכני-בלבד.**

### 8. Evidence-based diagnosis + Drill Down חוצה-מקורות — רכיב מרכזי ✅
כל הכלים תומכים ב-Drill Down, אך תמיד סביב הישות המובנית שלהם (Issue/Transaction/Trace). **החלטה: לבנות Drill Down סביב מושג "Finding" עצמאי** שיכול להיווצר מכל שילוב אירועים (כולל בלי exception בכלל — למשל ירידת פעילות) ותמיד לחזור לראיות ממקורות מרובים.

### 9. Exception Grouping — נדרש, ברמת מספיקות ולא חדשנות ✅
Sentry הוא ה-benchmark (fingerprinting מבוסס stack-trace/type/message, כולל שכבת ML סמנטית חדשה יותר). **החלטה: לממש grouping סביר (stack-trace + exception-type + message-template hashing) ב-V1 — לא לנסות "לנצח" את Sentry בדיוק ה-grouping; להתמקד בכך שה-grouping מוזן לתוך מנגנון ה-Finding שלנו (עם baseline+context), לא רק ב-issue tracker נפרד.**

### 10. עצמאות מספק/ענן — יתרון תחרותי אמיתי ✅
היכולות המתקדמות ביותר בשוק (Smart Detection+Copilot Agent, Grafana ML/Sift/Asserts) נעולות מאחורי Azure או Grafana Cloud Enterprise. **החלטה: למקם את המוצר כ-self-hostable, לא תלוי בענן ספציפי** — זה תואם ישירות לדרישת האפיון (סעיף 17: "לא לנסות להחליף... Grafana... Application Insights", וגם דרישת ה-Generic Product בסעיף 2.1).

## שאלות פתוחות שדורשות החלטת ארכיטקטורה (לא נענו ממחקר השוק)

1. ❓ **מבנה ה-Ingestion API בפועל** — HTTP JSON קנייני בלבד? OTLP-first? שניהם? זה יוכרע בשלב Ingestion/API Design הבא, לא כאן.
2. ❓ **`service.namespace` כ-Required** — נמצאו מקורות חלוקים לגבי רמת ה-requirement המדויקת ב-spec הנוכחי של OpenTelemetry Semantic Conventions. יש לאמת שוב מול גרסת ה-spec הספציפית שתיבחר לפני שמתכננים מיפוי Application/Module מלא עליה.
3. ❓ **היקף ה-Baseline learning ל-V1** — סטטיסטיקה פשוטה (ממוצע+סטיית-תקן) מול משהו מתוחכם יותר? זו החלטת V1-scope, לא מחקר-שוק.
4. ❓ **Auto-instrumentation ל-.NET** — OTel .NET auto-instrumentation עדיין בבטא (ה-SDK הידני יציב לגמרי). אם התוכנית כוללת חיבור אפליקציות .NET קיימות בלי שינוי קוד, יש לקחת את זה בחשבון בתכנון ה-SDK/Client שלנו.
5. ❓ **קצב ההתקדמות של Sentry Seer / Azure Copilot Observability Agent** — אלה פיצ'רים חדשים (2026) שעדיין מתפתחים. יש לעקוב אחריהם בעת תכנון V2+ ולא רק V1, כי ה-benchmark התחרותי בתחום ה-AI-assisted diagnosis זז מהר.

## מה השלב הבא (לפי סעיף 23 של האפיון)

מחקר הכלים הקיימים (שלב 3) הושלם. השלבים הבאים לפי האפיון:
1. אפיון מוצר + הגדרת V1 (מתבסס ישירות על ה-Market Gap המחודד כאן)
2. Architecture (עם חלופות מנומקות)
3. Data Model — כולל ה-Application Model ההיררכי (ההחלטה החזקה ביותר מהמחקר, סעיף 4 למעלה)
4. Ingestion/API Design (מתבסס על החלטה #2 — Collector/adapter pattern ל-OTLP)
5. Analysis/Anomaly Detection Design (מתבסס על החלטות #5–#8 — במיוחד מודל Fact/Observation/Hypothesis/Conclusion, שהוא כרגע ההבדלה התחרותית החזקה ביותר שנמצאה)
6. UI Design, Security Design, Test Strategy, תוכנית עבודה

**לא להתחיל פיתוח קוד לפני שהשלבים האלה נבדקו ואושרו**, כפי שהאפיון קובע במפורש.

## מתודולוגיה

המחקר בוצע בשני שלבים:

1. **טיוטה ראשונית** — מחקר שנעשה באמצעות ChatGPT, שכיסה את שמונת התחומים שהאפיון דורש לבדוק עבור כל כלי (מה פותר / מה לא פותר / Data Model / Ingestion / Query / Correlation / Exceptions / Performance / Anomaly Detection / UX).
2. **אימות מול תיעוד רשמי** — כל טענה מהטיוטה נבדקה בנפרד מול האתר/תיעוד הרשמי של כל כלי (datalust.co, docs.sentry.io, learn.microsoft.com, grafana.com/docs, opentelemetry.io), על ידי חמישה סוכני מחקר עצמאיים (אחד לכל כלי), שחיפשו במפורש מקורות רשמיים וציטטו אותם.

לכל טענה במסמך זה יש סימון אימות:

| סימון | משמעות |
|---|---|
| ✅ מאומת | נמצא תואם באופן ישיר בתיעוד הרשמי, עם מקור מצוטט |
| 🟡 מאומת חלקית | הרעיון נכון אך דורש דיוק/הסתייגות — מפורט בטקסט |

**הערה מתודולוגית חשובה, בהתאם לעקרון "עובדות מול מסקנות" של האפיון עצמו:** גם לאחר אימות מול תיעוד רשמי, הממצאים כאן הם **Facts על בסיס תיעוד**, לא בהכרח **Facts על בסיס התנסות מעשית**. מוצרים כמו Sentry ו-Application Insights מוסיפים יכולות AI בקצב מהיר (ראו למשל Sentry Seer, Azure Copilot Observability Agent) — יש לצפות שחלק מהממצאים כאן יתיישנו תוך חודשים ספורים, ולסמן אותם מחדש כ"דורש אימות" בכל פעם שהם משמשים בסיס להחלטה ארכיטקטונית משמעותית.

## 1. Seq

**מקורות:** docs.datalust.co (An Overview of Seq, Built-in Properties, Getting Logs into Seq, The Seq Query Language, SQL Queries, Tracing, Signals, Alerts, Dashboards, Metrics, What's New)

### מה הוא פותר
שרת self-hosted (Windows / Docker-Linux) לחיפוש וניתוח בזמן אמת של structured logs, traces ו-(מ-2026.1) metrics. ✅ מאומת. אין ל-Datalust הצעת SaaS רשמית — "cloud" משמעו self-hosting על תשתית ענן, לא שירות מנוהל.

### Data Model
מודל שטוח: שדות `@`-מובנים קבועים (`@Timestamp`, `@Message`, `@MessageTemplate`, `@Exception`, `@EventType`, `@Level`, `@TraceId`, `@SpanId`, `@ParentId`, `@Elapsed` ועוד) + `@Properties` חופשי לגמרי. ✅ מאומת. **אין מודל היררכי מובנה של Application→Module→Screen→Process→Operation** — כל היררכיה כזו היא קונבנציה של המשתמש בלבד, ממומשת דרך properties. זו נקודת מוצא חשובה: אין ל-Seq שום "תפיסה" של מבנה אפליקציה.

### Ingestion
עשיר ומבוסס: Serilog, Microsoft.Extensions.Logging, OpenTelemetry (OTLP native, HTTP+gRPC), HTTP API גולמי, GELF, Syslog, Docker log driver, ו-`seqcli ingest` לייבוא קבצים. ✅ מאומת במלואו — Seq בשל מאוד בתחום הזה, אין טעם לשכפל.

### Query
שתי שפות: שפת סינון/חיפוש (`@Level = 'Error'`, regex, operators) + שפת ניתוח דמוית-SQL מלאה (`select ... from stream where ... group by ... having ...`) עם aggregates (count, mean, sum, distinct, percentile) ו-time-bucketing. ✅ מאומת. חזק מאוד — לא הייתי מנסה "לנצח" את Seq בתחום הזה.

### Correlation
תמיכת Tracing החל מ-2024.1: spans מקושרים ל-trace דרך `@TraceId`/`@ParentId`, עם ויזואליזציית waterfall. ✅ מאומת. **חשוב:** זהו כלי חקירה/ויזואליזציה ידני — אין שום היסק אוטומטי שמקשר אירועים; הקישור נעשה אך ורק דרך trace ID שהאפליקציה עצמה סיפקה.

### Exceptions
`@Exception` הוא שדה חופשי לחיפוש/סינון בלבד. ❓ **אין exception grouping/fingerprinting אוטומטי, אין ישות "Issue", אין מעקב occurrence-count מובנה** — כל זה דורש בנייה ידנית של query. זהו פער מובהק וברור מול Sentry.

### Performance
`@Elapsed` + aggregates (percentile/mean) מאפשרים ניתוח latency; Metrics כפיצ'ר ייעודי מ-2026.1. ✅ מאומת. **אין regression detection אוטומטי** — צריך להגדיר threshold alert ידני.

### Anomaly Detection — הממצא הקריטי ביותר
❌ **מאומת: אין שום יכולת סטטיסטית/baseline-learning בשום מקום במוצר**, כולל בפיצ'ר ה-Metrics החדש (2026.1). כל "detection" הוא query + `having`/threshold קבוע שהמשתמש כותב וקובע ידנית. הדבר הכי קרוב שנמצא: Seq Apps כמו `Seq.App.FirstOfType` ו-`Seq.App.UnseenValueAlert` — אלה מזהים "ערך/type שלא נראה קודם" (novelty detection), **לא** חריגה סטטיסטית ביחס להתנהגות רגילה. זו יכולת קרובה אך שונה מהותית ממה שהאפיון שלנו דורש.

### UX
Workflow מכוון Developer Investigation: Search → Filter → Inspect → Analyze → Correlate → Chart/Dashboard → Alert. ✅ מאומת.

### מה למדנו ש-GPT לא ציין
- **Signals** (saved/reusable filters עם group by) הם המנגנון בפועל של Seq ל"ארגון אפליקטיבי" של זרם האירועים — התחליף המעשי להיררכיה שאין ב-Seq.
- Datalust אינה מציעה SaaS רשמי — רלוונטי אם ההבדלה שלנו כוללת "אין צורך ב-self-hosting".

## 2. Sentry

**מקורות:** docs.sentry.io (Concepts/Key Terms, Releases, Environments, Grouping and Fingerprints, Event Grouping, Issue Details, Performance Issues/N+1, Trace Explorer, Alerts, Escalating Issues, Metric Alert Config, AI in Sentry/Seer), sentry.io/changelog, blog.sentry.io

### מה הוא פותר
פלטפורמת Error Monitoring + APM שהופכת exceptions גולמיים ל-**Issues** ניתנים לחקירה — לא רק לוג של exception. ✅ מאומת.

### Data Model
מודל ה"שרשרת" מהמחקר הראשוני מטעה מעט: **Event** בודד (occurrence אחד) נושא בו-זמנית stack trace + breadcrumbs + user context + release tag + environment tag + trace context — אלה תכונות על אותו Event, לא היררכיה סדרתית. אירועים דומים מקובצים ל-**Issue**, וה-Issue הוא זה שצובר occurrence count, first-seen, last-seen. 🟡 מאומת חלקית — הישויות אמיתיות, ה"שרשרת" הליניארית לא מדויקת.

### Exception Grouping — חוזקה מרכזית
✅ **מאומת ומאושש**: Sentry מחשב "fingerprint" אוטומטי (stack trace → exception type → message, בסדר עדיפות זה) ומקבץ events בעלי fingerprint זהה ל-Issue אחד, עם ספירת occurrences, first/last-seen, ניתן להתאמה ידנית (Fingerprint Rules). זהו בדיוק הכיוון שה-Finding model שלנו צריך ללמוד ממנו.

### Releases ו-Regression Detection
✅ מאומת: Release = גרסת קוד שנפרסה לסביבה; שלושה מנגנוני resolve ("Resolved in Current Release" / "Next Release" / "in a Commit") עם regression detection אוטומטי אם השגיאה חוזרת. **הסתייגות תיעודית:** יש דיווחי קהילה (GitHub issues) על באגי edge-case (timestamps לא-מסודרים גורמים ל-false regression) — שווה לזכור כמגבלת יישום, לא רק תיעוד.

### Performance / Tracing
✅ מאומת: Tracing מלא (spans, transactions) כמוצר נפרד לגמרי מ-error tracking, כולל detector אוטומטי ל-N+1 queries (rule-based על תבנית ה-spans, לא סטטיסטי).

### User Context ו-Breadcrumbs
✅ מאומת: Breadcrumbs = "trail of events" (clicks, navigation, HTTP, console) לפני השגיאה; User Context = זהות מצורפת לאירוע — שני מנגנונים נפרדים ומתועדים.

### Alerts
✅ מאומת: שני סוגים — **Issue Alerts** (state-based: new issue, frequency, regression — כולם **סטטיים/ידניים**) ו-**Metric Alerts** (aggregate metric חוצה threshold, עם אפשרות ML — ראו הבא).

### Anomaly Detection — הממצא הקריטי ביותר
✅ **מאומת ומשמעותי יותר מהטענה המקורית.** שני מנגנונים נפרדים, לא אחד:

1. **Escalating Issues Algorithm** — רץ אוטומטית על כל Issue, **ללא צורך בקונפיגורציה כלל**. מחשב "baseline spike limit"/"bursty limit" מתוך היסטוריית שבוע קודם (max hourly volume + coefficient of variation), ומסמן Issue כ-Escalating כשהוא חורג — בדיוק ה"חריגה ביחס ל-baseline היסטורי" שהאפיון שלנו דורש.
2. **Anomaly Detection ל-Metric Alerts** — מצב זיהוי אופציונלי ("Anomaly", לצד "Fixed Threshold"/"Percentage Change") מבוסס Matrix Profile + Prophet, מתחשב אוטומטית ב-seasonality וטרנד, 3 רמות רגישות, ללא קונפיגורציה נדרשת (בטא, לתוכניות בתשלום).

**הסתייגות חשובה:** רוב הארגונים עדיין משתמשים ב-Issue Alerts הרגילים (סטטיים) — היכולות המתקדמות קיימות אך לא בהכרח בשימוש דיפולטיבי.

### מה למדנו ש-GPT לא ציין — הפער הכי גדול במחקר המקורי
**Sentry Seer** (חבילת AI): **Autofix** (ניתוח root-cause אוטומטי + פתיחת PR עם תיקון מוצע; Sentry מדווחת ~94.5% דיוק בזיהוי root-cause עצמו), **Issue Summary** (הסבר בשפה טבעית שנוצר ב-LLM), Seer Agent שיחתי לחקירה חוצת-טלמטריה, וסיווג "Semantic Fingerprints" מבוסס ML ל-grouping (מעבר ל-stack-trace-matching גרידא). זהו כיוון תחרותי משמעותי — Sentry לא רק מזהה חריגה, היא כבר מנסה להסביר ולתקן אותה אוטומטית.

## 3. Application Insights

**מקורות:** learn.microsoft.com/azure/azure-monitor (App Insights Overview, Data Model Complete, Application Map, Distributed Trace Data, Failures-Performance-Transactions, Proactive Diagnostics/Failure Diagnostics/Smart Detection Performance/Memory Leak/Exception Volume, Dynamic Thresholds, Annotations, AIOps/Observability Agent Overview)

### מה הוא פותר
פיצ'ר APM בתוך Azure Monitor. ✅ מאומת.

### Data Model
טבלאות: `requests`, `dependencies`, `exceptions` (כולל stack trace מלא), `performanceCounters`, `customEvents`/`customMetrics`. ✅ מאומת, עם תוספת: גם `traces` (לוגים חופשיים), Availability, Browser timing, Page views, ומ-2026 גם `genAIContent` ל-telemetry של LLM/agents — רשימה רחבה יותר ממה שהמחקר המקורי ציין.

### Application Map — נקודה קריטית לעמדה התחרותית שלנו
✅ מאומת במלואו: מציג טופולוגיה מלאה (components + dependencies + health KPIs), עם edges שניתן לצבוע/לסנן לפי error rate, duration, call count. **זו כבר יכולת "Application Awareness" אמיתית ומיוצרת בשוק** — לא רעיון פנוי.

### "Intelligent View" — התיקון החשוב ביותר למחקר המקורי
✅ מאומת, והניחוש המקורי היה נכון בפועל, אך התבלבל בין שני פיצ'רים נפרדים:
1. **Intelligent View** (תת-פיצ'ר של Application Map) — מודל AIOps ML שמדגיש (באדום) edges משמעותיים במפה, מבוסס failure rate + request count + duration + anomalies + dependency type, עם dial רגישות (High/Medium/Low) במקום threshold קבוע.
2. **Smart Detection** — מערכת anomaly detection נפרדת ורחבה יותר (ראו הבא), לא רק על המפה.

### Correlation
✅ מאומת: `operation_Id`/`operation_ParentId` על כל פריט טלמטריה, ממופה מ-W3C Trace-Context, מזין את **Transaction Diagnostics** — Gantt chart אוטומטי חוצה requests/dependencies/exceptions לפעולה בודדת.

### Anomaly Detection — הממצא הקריטי ביותר בכל המחקר
✅ **מאומת, ומדויק יותר ומרשים יותר מהטענה המקורית.** "Smart Detection" הוא שם-מטריה למספר מודולים, **כולם ML-based, ללא threshold סטטי בכלל**, וכולם zero-configuration:

| מודול | מנגנון | חלון היסטוריה |
|---|---|---|
| Failure Anomalies | ML קנייני, סטיית תקן על 20 דק' מול 40 דק' + 7 ימים אחרונים | 24 שעות טעינה ראשונית |
| Performance Anomalies | ML/data-mining, response-time / dependency-duration / segment-specific | 8 ימים |
| Memory Leak Detection | ML על performance counters (Private Bytes) | חלון ארוך |
| Abnormal Exception Volume | השוואה ל-baseline של 7 ימים, מנוטרל לצמיחת שימוש טבעית | 7 ימים |

**זה בדיוק מה שהאפיון שלנו מבקש מ-Baseline learning** — כולל נטרול צמיחה טבעית ("להתחשב בעומסים"). **בנוסף** קיים **Dynamic Thresholds** (יכולת Azure Monitor כללית יותר, לא ספציפית ל-App Insights) עם מודל seasonality שבועי מפורש (נדרשות 3+ שבועות היסטוריה) — מתוחכם סטטיסטית יותר מ-Smart Detection עצמו.

### מה למדנו ש-GPT לא ציין — הפער הכי גדול בכל המחקר
**Azure Copilot Observability Agent** (2026, AIOps) — סוכן LLM שמעל Azure Monitor/App Insights: מאפשר שיחה בשפה טבעית עם הטלמטריה; מריץ "**Deep Investigations**" על-פי דרישה — אוסף סיגנלים חוצי app+infra+platform, **מקשר אוטומטית**, ומפיק דוח ממצאים + המלצות; ומריץ "**Autonomous Operations**" (preview) — מקשר אוטומטית alerts שמייצגים כנראה את אותו אירוע ל-"Azure Monitor issue" אחד, ברקע, במודל "controlled-autonomy" (לא משנה config בעצמו). **זהו כבר המימוש המתקדם ביותר בשוק למה שה-What's Unusual / Correlation Analysis של האפיון שלנו שואפים אליו** — עם Deployment/Release annotations כקלט מפורש לחקירה. גם Smart Detection עצמו עובר migration להיות מבוסס Alert rules רגילים (standardization).

**הערה חשובה לעמדה התחרותית:** בגלל הפיצ'ר הזה, אי אפשר להציג את "Application Awareness + Anomaly Detection + הסבר אוטומטי" כרעיון שאין בשוק — הוא קיים, ב-Azure, ברמה גבוהה. ההבדלה שלנו חייבת להיות עמוקה יותר (ראו מסמך Market Gap).

## 4. Grafana + Loki

**מקורות:** grafana.com/docs (Loki: Get Started/Overview, Architecture, Log Queries, Alert/Ruler; Grafana: Introduction; Grafana Cloud: Machine Learning, Sift, Adaptive Traces; grafana.com/blog)

### חלוקת אחריות
✅ מאומת: Loki = log aggregation engine בלבד; Grafana = שכבת ויזואליזציה/exploration/dashboards כללית (150+ data sources, לא רק Loki).

### מודל האינדוקס — ייחודי ומהותי להבין
✅ **מאומת כמעט מילה-במילה**: Loki **לא** מאנדקס תוכן לוג מלא. האינדקס (TSDB) מכיל רק labels + timestamp + הפניה ל-chunk; תוכן הלוג עצמו נשמר דחוס ב-chunks (באחסון object storage), וסינון תוכן (`|=`, `|~` וכו') מתבצע בסריקה בזמן query בתוך ה-streams שנבחרו לפי הלייבלים. זהו design שנועד ל-scale וחיסכון באחסון, במחיר grep-like scan על תוכן.

### Query — LogQL
✅ מאומת: log stream selector חובה (`{service="payment"}`) + pipeline של filters/parsers/label-filters/formatting.

### יתרונות
✅ מאומת: scale גבוה, multi-tenancy (בידוד מלא לפי `X-Scope-OrgID`), אינטגרציה ל-dashboards משולבים logs+metrics+traces (derived fields, exemplars — **דורשים חיווט ידני מהמשתמש, לא אוטומטי**), alerting על log queries דרך ה-ruler component.

### Anomaly Detection — הממצא הקריטי ביותר
🟡 **מאומת חלקית, עם הבחנה מהותית בין OSS לתשלום:**
- **Loki/Grafana OSS (חינמי, self-hosted): אין שום anomaly detection.** רק alert rules סטטיים דרך ה-ruler.
- **Grafana Cloud (בתשלום) בלבד** מוסיף: **Grafana ML** (forecasting/anomaly/outlier — **על metric queries בלבד**, כלומר על מספרים שנגזרו מלוגים, לא על תוכן הלוג הגולמי; tier בתשלום). **Sift** (חינמי בכל חשבון Cloud, אך **human-triggered per-investigation** — לא רץ ברקע כל הזמן — מזהה קפיצות ב-error patterns שהוא עצמו מקבץ מהלוגים). **Adaptive Traces** (baseline אוטומטי ברירת מחדל — אך **ל-traces בלבד**, לא logs). **Asserts/Knowledge Graph** (enterprise, root-cause חוצה-סיגנלים אוטומטי — הכי קרוב ל-What's Unusual שלנו, אך add-on יקר).

**מסקנת ביניים:** "צריך בן אדם שיסתכל על dashboard" זה תיאור הוגן ל-OSS core, אבל הכללה-יתר לכל ה-ecosystem בתשלום.

### מה למדנו ש-GPT לא ציין
**Loki Pattern Ingester / "Logs Drilldown"** (Loki 3.0+) — מזהה ומקבץ אוטומטית תבניות מבניות מתוך שורות לוג גולמיות (masking טוקנים משתנים), **ללא labels או קונפיגורציה מהמשתמש** — יכולת discovery-מבנה-אוטומטי רלוונטית ישירות ל"הבנת מבנה לוגי" שהאפיון שלנו דורש, שהמחקר המקורי פספס לגמרי.

## 5. OpenTelemetry

**מקורות:** opentelemetry.io/docs (What is OpenTelemetry, Collector, Concepts/Signals/Traces, Context Propagation, Concepts/Signals/Logs, Logs Data Model spec, Languages/.NET, Zero-code/.NET, Specs/OTLP, Collector/Extend/Custom Receiver, Collector/Custom Collector, Specs/Semconv/Resource/Service, Specs/Semconv/General/Logs)

### מהות
✅ מאומת במפורש ומילולית: "OpenTelemetry is not an observability backend" — תקן CNCF ניטרלי לייצור, איסוף וייצוא telemetry (traces/metrics/logs). Backend וויזואליזציה מושארים בכוונה לכלים אחרים.

### ארכיטקטורה
✅ מאומת: Application → OTel SDK → (אופציונלי) Collector (receive/process/export) → Backend(ים), דרך OTLP.

### Traces / Spans / Context Propagation
✅ מאומת: Trace = מסלול בקשה; Span = יחידת עבודה, יכול לקנן; כל spans של אותו trace חולקים `trace_id`, כל span מקבל `span_id` ייחודי + `parent_id`. Context Propagation ("הליבה שמאפשרת Distributed Tracing") מעביר את ה-IDs האלה בין תהליכים/שירותים דרך W3C TraceContext headers.

### בגרות Logs — ניואנס חשוב
🟡 מאומת חלקית: ה-**spec** של Logs Data Model הוא Stable — לא נחות מ-traces/metrics ברמת התקן. אבל **בגרות ה-SDK משתנה לפי שפה**: C++/.NET/Java/PHP יציבים; Go/Rust בבטא; JS/Python/Ruby/Swift עדיין בפיתוח. **עבור .NET ספציפית (הרלוונטי לנו) — Logs יציב במלואו**, כך שהחשש הזה לא רלוונטי לנו בפועל.

### תמיכת .NET
✅ מאומת: Traces + Metrics + Logs כולם **Stable** ב-.NET (SDK/instrumentation ידני). **הסתייגות:** Auto-instrumentation ("zero-code") ל-.NET עדיין **בטא** — רלוונטי אם התוכנית כוללת auto-instrumentation של אפליקציות קיימות בלי שינוי קוד.

### היעדר יכולות Backend
✅ מאומת: אין query, dashboards, alerting, anomaly detection — הכל באחריות ה-backend, כצפוי מ-framework ניטרלי.

### עלות/תועלת של תאימות OTLP — ניתוח שנעשה במיוחד עבורנו
OTLP הוא פרוטוקול מוגדר-היטב (gRPC על 4317, HTTP+protobuf/JSON על 4318). **המסקנה המעשית מהתיעוד הרשמי (Collector's "Build a receiver" guide):** הדרך הזולה ביותר להיות "OTel-compatible" **אינה** לממש שרת OTLP מאפס, אלא **להריץ OpenTelemetry Collector כשער כניסה** עם exporter מותאם-אישית שממפה את מודל הנתונים של OTel (resource/log/span) לסכימה הפנימית של המוצר שלנו — כלומר "כתיבת adapter אחד" במקום "מימוש פרוטוקול מלא". זו המלצה ישירה לארכיטקטורה.

### מיפוי סמנטי רלוונטי להיררכיה שלנו
✅ מאומת: `SeverityText`/`SeverityNumber` (1-24, TRACE→FATAL) ניתן לאמץ ישירות. `service.name` (Required) ו-`service.namespace` (Required לפי הגרסה הנוכחית של הספק — **דורש אימות חוזר מול גרסת ה-spec המדויקת שנבחר, כי מקורות שונים חלוקים על רמת ה-requirement**) ממפים באופן טבעי ל-Service/Module. **חשוב:** מודל OTel הוא **דו-שכבתי בלבד** (namespace + name) — כל שכבה שלישית ("Application" מעל Module) היא הרחבה קניינית שלנו, לא משהו שה-semantic conventions כבר נותנים.

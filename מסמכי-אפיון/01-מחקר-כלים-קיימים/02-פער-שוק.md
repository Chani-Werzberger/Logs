## הערה פתיחה חשובה

המחקר הראשוני (טיוטת GPT) הניח שהפער המרכזי בשוק הוא "אף כלי לא באמת עושה Application Awareness + Baseline + Anomaly Detection + Finding עם ראיות". **לאחר אימות מול תיעוד רשמי, ההנחה הזו נכונה רק בחלקה.** שני כלים — Application Insights ו-Sentry — כבר מממשים חלקים משמעותיים מזה, ברמה גבוהה יותר ממה שההנחה המקורית שיערה. זהו הממצא הכי חשוב של שלב המחקר, ולכן הוא נדרש לעיצוב-מחדש (לא ביטול) של תזת הפער.

זה בדיוק המקרה שהאפיון עצמו מזהיר מפניו: השערה ראשונית לא הפכה עדיין למסקנה מבוססת-ראיות. עכשיו יש ראיות, וצריך לעדכן את ה-Hypothesis בהתאם.

## מה כבר קיים היטב בשוק (מכוסה, לא כדאי לבנות מחדש)

| יכולת | מי כבר עושה את זה טוב | האם שווה להתחרות בזה? |
|---|---|---|
| חיפוש/סינון structured logs, שפת query עוצמתית | Seq (חזק במיוחד), Grafana/Loki, App Insights (KQL) | לא — לבנות סינון סביר, לא לנסות "לנצח" |
| Ingestion רב-ערוצי (Serilog, OTel, HTTP, SDKs) | Seq, OpenTelemetry (כתקן), כולם | לא — לאמץ תקנים קיימים (OTLP), לא להמציא מחדש |
| Exception grouping/fingerprinting אוטומטי | Sentry (חוזקה מרכזית, כולל semantic/ML grouping) | לא לבנות algorithm מתחרה — ללמוד מהעיקרון, ליישם גרסה מספיקה |
| Distributed tracing / Correlation ID / Trace ID | Seq, Sentry, App Insights, OpenTelemetry (כתקן) | לא — Correlation ID/Trace ID הם **חובה** אצלנו, אבל כמנגנון סטנדרטי, לא כחידוש |
| Dashboards / ויזואליזציה כללית | Grafana (חוזקה מובהקת) | לא — האפיון עצמו קובע שזה לא מטרת V1 |
| **Application topology map (מי קורא למי)** | **Application Insights (Application Map) — קיים ומיוצר** | לא כרעיון-בפני-עצמו; רק אם יש לו זווית Application-Aware עמוקה יותר (ראו למטה) |
| **Baseline-learning anomaly detection (ML, zero-config, מתחשב ב-seasonality)** | **Application Insights (Smart Detection + Dynamic Thresholds) ו-Sentry (Escalating Issues + Metric Anomaly Detection) — קיים ומיוצר, לא רעיון תיאורטי** | לא כרעיון-בפני-עצמו — "אנחנו מזהים חריגות מול baseline" **לבד** אינו עוד סיבה מספקת לבנות מוצר חדש |
| **חקירה/הסבר אוטומטי מבוסס AI חוצה-סיגנלים** | **Sentry Seer (Autofix, Issue Summary) ו-Azure Copilot Observability Agent (Deep Investigations, Autonomous Operations) — קיים, חדש (2026), ומתקדם** | לא — זה כבר frontier מתקדם של ספקים גדולים עם משאבי ML עצומים |

**המסקנה החדה מכאן:** שלושה מתוך ארבעת "עמודי התווך" שהמחקר המקורי הציע כייחוד שלנו (Application Awareness, Baseline, Anomaly Detection, הסבר אוטומטי) **קיימים כבר בשוק ברמה גבוהה** — אצל ספק ענן אחד לפחות (Microsoft) ואצל ספק error-tracking מוביל (Sentry). זה לא אומר שאין מקום למוצר — זה אומר שהמקום הוא **צר וממוקד יותר** ממה שההנחה הראשונית שיערה.

## מה עדיין באמת חסר — הפער האמיתי לאחר האימות

### 1. אף כלי לא מפריד במפורש בין Fact / Observation / Hypothesis / Conclusion
זהו הפער **הכי חד** שנמצא במחקר, ואף אחד מהכלים — כולל App Insights ו-Sentry המתקדמים ביותר — לא ממש אותו:
- Smart Detection של App Insights **מציג ממצא כאילו הוא כבר "אמת"** (למשל "Failure Anomaly detected") בלי להפריד את המדידה עצמה (X% כשל ב-20 דקות) מהפרשנות שלה (זה "anomaly").
- Sentry Seer's Autofix **מציע תיקון קונקרטי (PR)** מבלי לחייב אימות מפורש שה-root cause באמת הוכח — 94.5% דיוק זה עדיין לא 100%, ואין בממשק הפרדה שקופה בין "זו עובדה" ל"זו השערה שה-AI מציע".
- Azure Copilot Observability Agent מייצר "דוח ממצאים + המלצות" — נשמע קרוב, אך התיעוד לא מתאר structure מפורש של Fact→Observation→Hypothesis→Conclusion שהמשתמש יכול לבחון directly ולדעת מה הוכח ומה לא.

**זה נשאר יתרון תחרותי אמיתי**, כי הוא לא טכני-בלבד אלא עיצובי/אפיסטמי — משמעו התחייבות מוצרית שלא להציג ניחוש כעובדה, שהאפיון שלנו מגדיר כעיקרון-על (סעיף 2.3).

### 2. אף כלי אינו Generic/Vendor-neutral באמת ברמת מודל האפליקציה
- Application Insights = Azure בלבד.
- Sentry = מוצר סגור, מודל Project/Environment שטוח יחסית — לא מגדיר Module→Screen→Service→Process→Operation.
- Grafana/Loki = OSS פתוח יחסית, אבל אין בו שום מודל "אפליקציה" — Labels שטוחים בלבד.
- Seq = אותו דבר — Properties שטוחים.
- OpenTelemetry = מגדיר רק **שתי** רמות (`service.namespace` + `service.name`) — לא תומך בהיררכיה עמוקה יותר (Application → Module → Screen/Service → Process → Operation) שהאפיון שלנו דורש.

**אף אחד מהכלים לא נותן למשתמש להגדיר בעצמו את המבנה הלוגי המלא של האפליקציה שלו ולנתח דרכו** — זה תמיד גנרי-שטוח (Loki/Seq) או ספציפי-לענן-אחד (App Insights) או ספציפי-למוצר-סגור (Sentry).

### 3. יכולות ה-Anomaly Detection המתקדמות ביותר נעולות מאחורי vendor lock-in או תשלום כבד
- Smart Detection + Copilot Observability Agent = Azure בלבד, ולא כל ארגון יכול/רוצה לעבור ל-Azure Monitor.
- Grafana ML / Sift / Adaptive Traces / Asserts = **כולם Grafana Cloud בתשלום**, וחלקם Enterprise-tier יקר; ה-OSS החינמי (Loki+Grafana עצמאי) חסר לגמרי.
- Sentry Anomaly Detection (Metric Alerts) = בטא, בתוכניות בתשלום.

יש כאן מקום למוצר שמביא יכולת דומה (baseline + anomaly + הסבר) **כמוצר עצמאי, self-hostable, לא קשור לענן ספציפי או לתשלום Enterprise** — זה מתיישר עם דרישת האפיון ל"מוצר גנרי, פרקטי, self-hosted-friendly".

### 4. Drill Down חוצה-מקורות מאורגן סביב "Finding" כמושג מרכזי, לא כתוצר-לוואי
בכל הכלים, Drill Down קיים אבל תמיד סביב ה-**ישות הטבעית של הכלי עצמו** (Issue אצל Sentry, Transaction אצל App Insights, Trace אצל Seq). אף אחד לא בונה סביב מושג "Finding" עצמאי שיכול להיווצר גם בלי exception (למשל: ירידת פעילות, שינוי דפוס משתמשים, קומבינציית אירועים חשודה) ולתמוך אותו בראיות מכמה מקורות במפורש. זה מתקשר ישירות לדרישת האפיון (סעיף 10) ש"המערכת אמורה לזהות... פעילות שנעלמה... שילוב אירועים שאינו אופייני" — לא רק ספייקים בשגיאות.

### 5. Loki Pattern Ingester ו-Sift מרמזים על כיוון עתידי — לא מיצוי
זיהוי תבניות אוטומטי מתוכן לוג גולמי (ללא labels/config) הוא כיוון חדש יחסית גם ל-Grafana עצמה (Loki 3.0+). זה מראה שהשוק בכלל עדיין לא מיצה את הכיוון של "המערכת מבינה בעצמה את מבנה הלוג" — יש כאן מרחב פתוח.

## הגדרת פער השוק המחודדת (Revised Market Gap Statement)

> קיימים כיום כלים חזקים מאוד לאיסוף, אחסון, חיפוש וניטור של Logs/Metrics/Traces (Seq, Grafana/Loki), וכן כלים מתקדמים לאבחון אוטומטי מבוסס-baseline וקיבוץ תקלות (Sentry, ואף יותר — Application Insights, שכולל כיום גם Application Map, Smart Detection ואפילו סוכן AI לחקירה אוטונומית חוצת-שכבות). לכן **אי אפשר עוד לטעון של-"Application Awareness + Baseline + Anomaly Detection" כרעיון אין בשוק** — הוא קיים, בעיקר בענן של Microsoft.
>
> הפער האמיתי שנותר הוא **שילוב ספציפי של ארבעה עקרונות שאף כלי לא ממש יחד**:
> 1. **מודל אפליקציה גנרי, מוגדר-משתמש, עמוק (Application→Module→Screen/Service→Process→Operation)** — ולא רק namespace+name שטוח או service map אוטומטי.
> 2. **הפרדה מוצרית מפורשת בין Fact / Observation / Hypothesis / Conclusion** בכל ממצא שהמערכת מציגה — לא רק "AI אמר" אלא שקיפות איזה חלק הוכח ואיזה עדיין השערה.
> 3. **עצמאות מספק ענן/מוצר-סגור** — יכולת baseline+anomaly detection שאינה כלואה מאחורי Azure או Grafana Cloud Enterprise.
> 4. **Finding כמושג-על עצמאי** שיכול להיווצר מכל שילוב אירועים (לא רק exception spike), עם Drill Down שתמיד חוזר לראיות המקוריות מכמה מקורות בו-זמנית.
>
> זהו מוצר צר וממוקד יותר מהתפיסה הראשונית, אבל הפער האמיתי — לא רק תפיסתי.

## סיכונים לתזת המוצר שיש להישמר מהם

1. **אל תציגו "אנחנו מזהים אנומליות" כערך מוצרי עצמאי** — זה כבר קיים, טוב, ב-Azure ו-Sentry. הערך חייב להיות בשילוב (מודל אפליקציה + שקיפות אפיסטמית + עצמאות ספק), לא ביכולת הבודדת.
2. **קחו בחשבון ש-Sentry Seer ו-Azure Copilot מתקדמים במהירות רבה** — ה-benchmark הזה יזוז. יש לתכנן V1 עם יעדים ריאליים (ראה מסמך V1) ולא לנסות "להדביק" יכולות AI מלאות מהיום הראשון.
3. **"Generic/Application-Aware" לבדו אינו מספיק ייחודי** — Application Insights כבר עושה טופולוגיה אוטומטית. הייחוד חייב להיות במודל **הנשלט-על-ידי-המשתמש** (הגדרה ידנית/גמישה של המבנה הלוגי), לא רק בגילוי אוטומטי.
4. **צריך לאמת מחדש כל הנחה קריטית לפני שהיא נכנסת לארכיטקטורה** — הממצאים כאן מבוססי תיעוד בלבד (לא ניסיון מעשי), ומוצרי AI/ML מתעדכנים מהר.

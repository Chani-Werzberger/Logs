# M3: Query API + Investigation UI — Design

**Status:** Approved by user, ready for implementation planning
**Part of:** Milestone M3 per `12-תוכנית-עבודה-ואבני-דרך.md` — the first UI-facing milestone that lets a person actually look at ingested log data. M0 (scaffolding), M1 (Application Model), and M2 (Ingestion API + `LogsPlatform.Client` + Serilog sink) are merged to `main`. M3 builds directly on M2's `Event`/`ExceptionGroup` tables — no schema changes.

## Goal

Query API (`GET /api/v1/events`, `/events/{id}`, `/timeline`, `/exception-groups`, `/exception-groups/{id}`) plus three UI screens (Search, Timeline, Exceptions) that let a person manually search, filter, and drill down through data M2 already ingested. Acceptance criterion is manual verification against M2-ingested data, per `12-תוכנית-עבודה-ואבני-דרך.md`'s M3 row — not an automated scenario test (that's M5).

**Explicitly out of scope** (per `09-UI-Design.md` and `12-תוכנית-עבודה-ואבני-דרך.md`): "What's Unusual"/Findings (M4, depends on the not-yet-built Analysis Engine), Login/session auth/`IsAdmin` gating (M6), retrofitting the existing Admin API's error responses to the new format, SQL Server full-text indexing, and Timeline's Finding-arrival highlighting (there are no Findings yet to arrive from).

## Query API

New read endpoints on `LogsPlatform.Web`, following the project's existing controller → repository pattern — no new architectural layer, no new project.

- **`GET /api/v1/events`** — `applicationId` and `environmentId` are required query params; optional: `from`/`to` (UTC `DateTime`), `severity`, `moduleId`/`screenServiceId`/`processId`/`operationId`, `correlationId`, `traceId`, `userId`, `customerId`, `exceptionGroupId`, `versionId`, `durationMinMs`/`durationMaxMs`, `q` (matched via `Message.Contains(q)`), `page` (default 1) and `pageSize` (default 50, max 200 — a request for more is clamped, not rejected). Response: `{ items: EventSummary[], totalCount: int }`, ordered by `Timestamp` descending. `EventSummary` carries the Search table's columns (id, timestamp, severity, full operation path, message, durationMs, correlationId) — not every field; full detail is `GET /api/v1/events/{id}`.
- **`GET /api/v1/events/{id}?applicationId=`** — `applicationId` is a required query param (the UI always has one in context from the top-bar selector). Single event, every column including `MetadataJson` and `StackTrace`. 404 if the id doesn't exist or its `ApplicationId` doesn't match the supplied one (IDOR guard, matching every other single-resource endpoint in the project).
- **`GET /api/v1/timeline`** — exactly one lookup mode must be supplied: `correlationId=` **or** `traceId=` **or** `operationId=`+`userId=` together **or** `customerId=`. Zero modes, or more than one, is a 400. Returns matching events ordered by `Timestamp` ascending (chronological story, not a browsable list) — no paging; a timeline is a bounded set by construction (one correlation chain, one trace, one user's activity on one operation, or one customer), not something that grows unbounded like the general event stream.
- **`GET /api/v1/exception-groups`** — `applicationId` required (an `ExceptionGroup` is Application-scoped only — no `EnvironmentId` column — so unlike every other Query API endpoint, this one does *not* take `environmentId`: a group's linked events may span environments, and the list intentionally shows the application's exception groups as a whole); optional `from`/`to` filtering on `LastSeenAt`; `sortBy` = `LastSeenAt` (default) or `OccurrenceCount`. Each item includes a `DailyCounts` array — always the most recent 14 days of event-count-per-day for that group (a fixed rolling window, independent of the list's own `from`/`to` filter, which only decides which *groups* appear, not the sparkline's range) — used to render the sparkline, and the distinct affected Operation names derived from its linked `Event` rows (per `09-UI-Design.md` §6's "Applications/Operations מושפעים" — the "Applications" half is redundant here since the list is already scoped to one `applicationId`, so only Operations varies per group).
- **`GET /api/v1/exception-groups/{id}`** — group detail: `RepresentativeStackTrace` in full, the same `DailyCounts` trend data (rendered larger), and the distinct `Application`/`Environment`/`Version`/`Operation` combinations seen among its linked `Event` rows (derived via a grouped query over `Events`, not stored separately).

**Error format**: the 5 endpoints above return ASP.NET Core's built-in `ProblemDetails` shape (`type`/`title`/`status`/`detail`, plus `errors` for validation failures) for every 4xx/5xx they produce — via `builder.Services.AddProblemDetails()` and the standard `ValidationProblem`/`Problem()` result helpers already built into the framework, not custom middleware. This applies only to these 5 endpoints; the existing Admin API's error responses are unchanged.

**New repository methods** (composed EF Core `IQueryable` chains — conditionally apply `.Where()` per supplied filter, same shape every repository in the project already uses, just wider):
- `IEventRepository`: `QueryAsync(EventQueryParameters) → (IReadOnlyList<Event> Items, int TotalCount)`, `GetByIdAsync(long id) → Event?`, `GetTimelineAsync(TimelineQuery) → IReadOnlyList<Event>`.
- `IExceptionGroupRepository`: `QueryAsync(ExceptionGroupQueryParameters) → (IReadOnlyList<ExceptionGroup>, int TotalCount)`, `GetByIdAsync(long id) → ExceptionGroup?`, `GetDailyCountsAsync(long exceptionGroupId, int days) → IReadOnlyDictionary<DateOnly, int>`.

`EventQueryParameters`, `TimelineQuery`, and `ExceptionGroupQueryParameters` are plain parameter-object records living alongside their repository interfaces, mirroring every other typed-parameter pattern already in `LogsPlatform.Domain`.

## UI

A new shared layout for the investigation area (distinct from the existing Admin section's layout) with a persistent top bar: an Application dropdown, then an Environment dropdown scoped to the chosen Application (populated from the existing Admin data — no new tables), always visible per `09-UI-Design.md` §9's "constant visual reminder of environment isolation." Top nav has exactly three links: **Search**, **Exceptions**, **Admin** (already exists, unchanged) — no standalone Timeline entry, matching `09-UI-Design.md` §2's explicit "Timeline has no independent nav entry, always reached in context." Selected `applicationId`/`environmentId` flow as route/query parameters into each page — the same convention `ModulesAdmin.razor` etc. already use for `{AppId:int}` — so every URL is shareable/bookmarkable and drill-down links are just constructed URLs, not shared component state. Since there's no login yet (M6), the Admin link is unconditionally visible — that gating is explicitly deferred, not an oversight.

- **Search** (`/search`): filter panel (time range, severity, cascading Module→ScreenService→Process→Operation pickers where each layer's options depend on the layer above, CorrelationId/TraceId/UserId/CustomerId/ExceptionGroupId/Version, duration min/max, free-text box) mapped directly onto `GET /api/v1/events`'s query params. Results table: Timestamp, Severity, full Operation path, truncated Message, Duration, CorrelationId — with Previous/Next paging driven by the response's `totalCount`. Clicking a row opens a side panel with every field from `GET /api/v1/events/{id}`, `MetadataJson` pretty-printed, `StackTrace` if present, and a "View Timeline" button (navigates to `/timeline?correlationId=...` using that event's `CorrelationId`, falling back to `traceId` if `CorrelationId` is null).
- **Timeline** (`/timeline?correlationId=...` / `?traceId=...` / `?operationId=...&userId=...` / `?customerId=...`, no nav entry): chronological list — relative time from the first event (`+0ms`, `+812ms`, ...), Operation, Severity, Duration, truncated Message.
- **Exceptions** (`/exceptions`): list — fingerprint (truncated), ExceptionType, OccurrenceCount, FirstSeen/LastSeen, a small inline SVG sparkline built from `DailyCounts` (a `<polyline>` over normalized points, no charting library/dependency), and the distinct affected Applications/Operations — sorted by LastSeenAt by default, toggleable to OccurrenceCount. Clicking a group opens `/exceptions/{id}`: full stack trace, the same trend data rendered as a larger sparkline, and a recent-occurrences table whose rows link to `/search` pre-filtered by that `exceptionGroupId`.

## Testing

Same convention as every prior plan in this project: real SQL Server LocalDB via `TestWebApplicationFactory`/`TestDatabase`, no mocking. Query API integration tests seed data through the real ingestion endpoint (`POST /api/v1/ingest/events`, dogfooding M2) rather than inserting rows directly, then assert the query/filter/pagination/timeline-mode-validation behavior through the new endpoints. UI gets integration-level tests against the underlying repositories/query logic directly (this codebase has no existing bUnit precedent for Blazor component tests, so introducing one is out of scope here — component-level UI testing isn't part of this plan). Kept to core-behavior-plus-one-edge-case per the project's standing test-volume guidance, not exhaustive filter-combination coverage.

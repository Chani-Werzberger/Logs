# M4a: Analysis Engine Core — Design

**Status:** Approved by user, ready for implementation planning
**Part of:** Milestone M4 per `12-תוכנית-עבודה-ואבני-דרך.md` — split into two plans given M4's substantially higher complexity than M1-M3 (real statistical algorithms, first `BackgroundService`, first non-CRUD business logic in the project). M4a is the algorithmic core: Baseline calculation, the 3 detectors, the 2 correlators, dedup, and the orchestrating `BackgroundService`. M4b (Findings API, lifecycle actions, the "What's Unusual" + Finding-detail UI) is a separate plan, brainstormed after M4a is built and merged — the same sequencing M2a/M2b used.

M0-M3 are merged to `main`. This plan builds directly on M1's Application hierarchy and M2/M3's `Event`/`ExceptionGroup` tables — no changes to either.

## Goal

Implement `08-Analysis-ו-Anomaly-Detection.md`'s detection logic end-to-end: a daily Baseline-learning phase, a 5-minute detection phase running 3 detectors, 2 correlators that augment newly-created Findings with hypotheses, and dedup so a persisting anomaly doesn't spawn a new Finding every 5 minutes. Acceptance criterion (per `12-תוכנית-עבודה-ואבני-דרך.md`'s M4 row): a manual run against hand-injected data produces a Finding with a valid Fact/Observation/Hypothesis chain. The full 6-scenario/0-false-positive proof is M5's job, not M4a's.

**Explicitly out of scope**: the Findings Query API, the Acknowledge/Resolve/Dismiss/Promote-to-Conclusion lifecycle actions, and the "What's Unusual"/Finding-detail UI screens — all M4b. `SyntheticDataGenerator` and the full scenario test — M5.

## Corrected `Finding.Type` enum

`05-מודל-נתונים.md`'s schema listing (`ErrorSpike | MissingActivity | CustomerAnomaly | DeploymentCorrelation | DownstreamFailure`) contradicts `08-Analysis-ו-Anomaly-Detection.md`'s actual detector/correlator logic — correlators augment an *existing* Finding with a `Hypothesis` statement (§4's opening line: they never create their own Finding), and §3 requires `PerformanceDegradation` and `NewException` as real, distinct types that `05`'s enum omits entirely. This plan treats `08` as authoritative: `Finding.Type ∈ {ErrorSpike, MissingActivity, PerformanceDegradation, NewException, CustomerAnomaly}` — exactly the 5 types §10's scenario-mapping table names as detector output. `DeploymentCorrelation`/`DownstreamFailure` are not Finding types anywhere in this plan.

## Added `EnvironmentId` scoping (a real gap in `08`, not just a naming fix)

`08`'s algorithms compute Baseline and detect anomalies "per Operation/ExceptionGroup" with no mention of Environment at all. This is a real correctness gap, not just an omission of detail: `Operation` is shared across every Environment of an Application (it's part of the application hierarchy, not per-environment), so without Environment scoping, a Staging deploy's erratic low-volume traffic would corrupt the *same Operation's* Production baseline, and a genuine Production spike could get diluted by quiet Staging data — silently defeating the whole point of baseline learning. This project has treated Environment isolation as a first-class principle since M1 (repository-layer isolation "from day one," the UI's persistent Application+Environment selector, M3's Query API requiring `environmentId` on nearly every endpoint) — Baseline/Finding not doing the same would be a real, surprising departure. This plan adds `EnvironmentId` (int, FK) to both `Baseline` and `Finding`, and every detector/correlator scopes its work per `(ApplicationId, EnvironmentId, ...)`, not just `(ApplicationId, ...)`. This also directly resolves what would otherwise be an awkward gap in `DeploymentCorrelator` (see below) — with `Finding.EnvironmentId` populated directly from the triggering `Event` rows, the correlator can look up `Deployment`s for that exact `(ApplicationId, EnvironmentId)` pair without any indirect joins.

`Customer` itself has no `EnvironmentId` (per its M1 schema — a customer is Application-scoped, not per-environment), but the *Events* referencing a customer do, so `CustomerOutlierDetector`'s peer-rate comparison is scoped per Environment too (comparing a customer's Production behavior against Production peers, not diluted by Staging noise).

## Data Model

Four new entities, all `Application`-scoped:

- **`Baseline`**: `ApplicationId` (int, FK), `EnvironmentId` (int, FK — this plan's addition, see above), `ScopeType` (enum: `Operation`|`ExceptionGroup`), `ScopeId` (`long`, intentionally unenforced FK — polymorphic per `05`'s own stated trade-off in §6), `MetricType` (enum: `EventCount`|`ExceptionCount`|`DurationMs`), `BucketHourOfDay` (0–23), `MeanValue` (double), `StdDevValue` (double), `SampleCount` (int), `LastUpdatedAt` (DateTime). Unique per `(ApplicationId, EnvironmentId, ScopeType, ScopeId, MetricType, BucketHourOfDay)`.
- **`Finding`**: `ApplicationId` (int, FK), `EnvironmentId` (int, FK — this plan's addition, see above; populated from the `Event` row(s) that triggered detection), `Type` (enum, corrected set above), `ScopeType`/`ScopeId` (same shape as `Baseline`'s — **this pair is also this plan's addition to `05`'s schema**, required for the dedup rule in §8 to be queryable at all), `Title` (string), `DetectedAt` (DateTime), `Severity` (enum — see "Severity computation" below), `ConfidenceLevel` (enum: `Low`|`Medium`|`High`), `Status` (enum: `New`|`Acknowledged`|`Resolved`|`Dismissed` — M4a only ever writes `New`; the other three states are M4b's lifecycle actions to set).
- **`FindingStatement`**: `FindingId` (long, FK), `Kind` (enum: `Fact`|`Observation`|`Hypothesis`|`Conclusion`), `Text` (string), `OrderIndex` (int), `ApprovedBy` (`string?`), `ApprovedAt` (`DateTime?`) — the last two are always null coming out of M4a; only M4b's explicit promotion action ever sets them, and only on a row already present as `Hypothesis` being flipped to `Conclusion` (never written as `Conclusion` from creation).
- **`Evidence`**: `FindingId` (long, FK), `EvidenceType` (enum: `Event`|`ExceptionGroup`|`Deployment`|`Baseline`|`Operation`), `ReferenceId` (long, unenforced FK, polymorphic per `EvidenceType`), `Description` (string).

No changes to `Event`, `ExceptionGroup`, or any M1 entity. `ExceptionGroup.OccurrenceCount`/`LastSeenAt` — reserved since M2a explicitly for this milestone to reconcile — are updated by the `NewExceptionDetector`'s scan pass (see below), not by ingestion.

## Algorithm Components

New `src/LogsPlatform.Web/Services/Analysis/` folder — this is the project's first non-CRUD business logic, kept isolated from the existing `Services/` files (`IngestionProcessor`, `HierarchyResolver`, etc.) since it's a genuinely different kind of code (statistical, batch-oriented, no HTTP request driving it).

- **`IMetricsRepository`** (new, `LogsPlatform.Domain.Repositories` + `LogsPlatform.Infrastructure` implementation) — analysis-only aggregate queries over `Event`, distinct from `IEventRepository`'s query-API concerns, all scoped by `(ApplicationId, EnvironmentId)`:
  - `GetHourlyEventCountAsync(int applicationId, int environmentId, int operationId, DateTime hourStart)` → int
  - `GetHourlyAverageDurationAsync(int applicationId, int environmentId, int operationId, DateTime hourStart)` → double?
  - `GetHourlyExceptionCountAsync(int applicationId, int environmentId, long exceptionGroupId, DateTime hourStart)` → int
  - `GetActiveOperationIdsAsync(int applicationId, int environmentId)` / `GetActiveExceptionGroupIdsAsync(int applicationId, int environmentId)` — what Baseline needs to iterate over, per environment
  - `GetCustomerRatesAsync(int applicationId, int environmentId, int? operationId, long? exceptionGroupId, DateTime windowStart)` → `IReadOnlyDictionary<int CustomerId, double Rate>` — for the Customer Outlier Detector's peer comparison

- **`BaselineCalculator`**: implements §2 exactly. For each active Operation (`EventCount`, `DurationMs`) and ExceptionGroup (`ExceptionCount`), for each hour 0–23: gather up to 28 daily samples via `IMetricsRepository`, compute `MeanValue`/`StdDevValue` (population stddev, since we have the full sample set, not an inferred population), upsert the `Baseline` row. `SampleCount < 14` still saves the row — it just carries forward into a `Confidence=Low` result downstream, never suppressed per `08`'s §9 principle #2.

- **`RateAnomalyDetector`**: for each `(Operation, MetricType)` and `(ExceptionGroup, ExceptionCount)`, computes the current hour's value, looks up the matching `Baseline` row, z-score `= (current - Mean) / max(StdDev, MIN_STDDEV_FLOOR)`. `z > SPIKE_THRESHOLD` → `ErrorSpike` (EventCount) or `PerformanceDegradation` (DurationMs). `z < -SPIKE_THRESHOLD AND Mean > MIN_MEANINGFUL_ACTIVITY` → `MissingActivity`. Produces `Fact` ("Operation X recorded Y in period Z") + `Observation` ("Nx the normal rate for this hour, baseline: Mean±StdDev, based on N days") statements, plus `Evidence` pointing at the `Baseline` row used.

- **`NewExceptionDetector`**: scans `ExceptionGroup`s with `FirstSeenAt` inside the current detection window (last 5 minutes) → `Finding(Type=NewException, Confidence=High, Severity=High)` immediately (§3.2: "we've never seen this" is a certain Fact, not a statistical estimate). `ExceptionGroup` itself has no `EnvironmentId` (it's Application-scoped, per M2a's schema — its linked `Event`s can in principle span environments); this detector resolves the new Finding's `EnvironmentId` from the triggering `Event` row(s) actually linked to the group within the window, and — in the (expected-rare) case a single newly-created group receives its first events from more than one environment in the same tick — creates one Finding per distinct `EnvironmentId` observed, keeping the "Finding is Environment-scoped" invariant intact rather than picking one arbitrarily. Also the point where `ExceptionGroup.OccurrenceCount`/`LastSeenAt` get reconciled against actual `Event` rows for groups touched this tick (per M2a's original design intent).

- **`CustomerOutlierDetector`**: peer-comparison, not self-historical (§3.3 — a brand-new customer has no baseline of its own to violate). For each `(Operation | ExceptionGroup)` with `>= MIN_PEER_CUSTOMERS` active customers in the window, compute each customer's rate, z-score against the *other* customers' population mean/stddev, `|z| > CUSTOMER_OUTLIER_THRESHOLD` → `Finding(Type=CustomerAnomaly)`.

- **`DeploymentCorrelator`**: for every newly-created `ErrorSpike`/`PerformanceDegradation`/`NewException` Finding this tick, looks for a `Deployment` on the same `(ApplicationId, EnvironmentId)` — straightforward now that `Finding.EnvironmentId` is populated directly (see "Added EnvironmentId scoping" above) — with `DeployedAt` inside `[DetectedAt - 60min, DetectedAt]`. If found: adds `Evidence(Deployment)` + a `Hypothesis` statement using the exact hedged phrasing from §4.1 ("ייתכן קשר, אך הוא לא אושר").

- **`DownstreamFailureCorrelator`**: for every new `NewException`/`ErrorSpike` Finding, looks for `Event` rows sharing the triggering event's `CorrelationId`, timestamped later, on a *different* Operation, with `Severity >= Error`. If found: adds `Evidence(Event)` per match + one `Hypothesis` statement summarizing the count and affected Operations, same hedged phrasing convention.

**Severity computation (a gap in `08` this plan resolves):** `08`'s §6 defines `ConfidenceLevel`'s algorithm in full but never defines `Severity`'s — §5's worked example just shows `Severity=High` without deriving it. Confidence and Severity answer different questions (how *sure* are we vs. how *bad* is it) and conflating them would make the field redundant, so this plan derives Severity independently, from the same z-score magnitude `RateAnomalyDetector`/`CustomerOutlierDetector` already compute: `|z| > 5 → High`, `3 < |z| <= 5 → Medium`, otherwise `Low` (this branch is only reachable via a detector's own threshold check, so in practice `Low` doesn't occur here — kept for completeness). `NewExceptionDetector` always sets `Severity=High` (a first-ever exception type is inherently worth attention regardless of volume, mirroring §3.2's Confidence=High reasoning).

- **`FindingWriter`**: the single choke point both detectors and both correlators call through — owns dedup (§8): before creating, checks for an existing `Status IN (New, Acknowledged)` Finding with the same `(ApplicationId, EnvironmentId, ScopeType, ScopeId, Type)`; if found and not past the cooldown window (24h since last `DetectedAt`), appends a new `Fact` statement to the existing Finding instead of creating a duplicate. This keeps the dedup rule in exactly one place rather than reimplemented per detector. Its statement-adding method takes a `DetectorStatementKind` (a *separate*, smaller enum: `Fact`|`Observation`|`Hypothesis` — deliberately without `Conclusion` as a possible value) rather than the full `FindingStatement.Kind` enum, and maps it 1:1 onto the entity's `Kind` when persisting. This makes `08`'s §1 promise ("the engine never writes Conclusion") a **compile-time impossibility for every caller in this plan**, not just a tested behavior — no detector or correlator can pass a value that doesn't exist. M4b's promotion action bypasses `FindingWriter` entirely and writes `Kind=Conclusion` directly via the repository, which is exactly the asymmetry the architecture wants: only the human-triggered path can reach that value at all.

- **`AnalysisEngineBackgroundService : BackgroundService`**: one process-wide timer loop (`PeriodicTimer`, 5-minute period — Phase 2's cadence), iterating every `(Application, Environment)` pair each tick — not scoped to a single application, since the whole point of this milestone is running across every application/environment the system knows about. Per `(Application, Environment)`: check whether any `Baseline` row for that pair has `LastUpdatedAt` from today; if not, run `BaselineCalculator` first for that pair (Phase 1), then always run the 3 detectors followed by the 2 correlators over that pair's newly-created Findings (Phase 2). The whole tick (all application/environment pairs) is guarded by one in-process flag (set at tick start, cleared at tick end) so a tick that's still running when the next one would fire is skipped, not run concurrently with itself — per `11-Test-Strategy.md`'s explicit requirement.

## Testing

Per `11-Test-Strategy.md`'s own M4-vs-M5 split (M5 owns the full 6-scenario/0-false-positive proof against `SyntheticDataGenerator`'s 40-day history; M4a proves the algorithms are individually correct against small, hand-crafted, known-distribution data):

- `BaselineCalculator`: seed exact known samples (e.g. a fixed set of 20 values with a hand-computed mean/stddev), assert the computed `Baseline` row matches within floating-point tolerance; separately assert `SampleCount < 14` still produces a saved row (not suppressed).
- One test per detector proving it fires on a hand-crafted anomaly (e.g. inject events at 6x the seeded baseline rate) and stays silent on in-range data.
- One test per correlator proving it attaches the expected `Hypothesis` + `Evidence` when a matching `Deployment`/downstream `Event` exists, and does nothing when none does.
- `FindingWriter` dedup: two detection ticks against the same persisting anomaly produce one `Finding` with two `Fact` statements, not two `Finding`s.
- A test confirming `DetectorStatementKind` (the enum `FindingWriter` accepts) has exactly the 3 non-`Conclusion` values and no more — the actual "engine can never write Conclusion" guarantee is enforced by the type system (see `FindingWriter` above), not by a runtime/reflection test; this test just guards against someone widening `DetectorStatementKind` back to the full 4-value enum later and silently reopening the gap.
- `AnalysisEngineBackgroundService`: a test proving a still-running tick causes the next scheduled tick to be skipped rather than run concurrently.

Real SQL Server LocalDB throughout, no mocking, per the project's standing convention — `IMetricsRepository`'s aggregate queries get seeded via direct `Event` inserts (matching `EventRepositoryQueryTests.cs`'s established pattern from M3), not through the ingestion HTTP endpoint, since these tests are about aggregate-query correctness, not the ingestion pipeline.
